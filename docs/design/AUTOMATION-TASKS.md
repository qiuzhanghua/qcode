# Qcode 定时任务（Scheduled Tasks）机制设计文档

> 本文档是 ADR-0059 的演进设计：把"配置文件声明的 cron 条目"扩展为一套完整的
> **运行时定时任务**系统——任务由模型或用户在运行中创建/管理，支持多种定时
> 规则，投递语义升级为"投递器"模型，并具备崩溃恢复能力。
>
> 结构：**第一部分**给出从任务创建到执行完毕再到崩溃恢复的宏观流程；**第二部分**
> 对每一步做设计详解（是什么 / 为什么）。所有内容都落在 Qcode 现有架构上（引擎
> 独立线程 + 单线程 tokio runtime、按会话隔离的 JSONL 日志、收件箱双队列、
> `SessionHost` 槽位），不引入新的运行时或新的会话模型。

## 1.2 环节概览

| 环节 | 一句话职责 | 核心组件 |
|---|---|---|
| ① 任务创建 | 模型/用户提交规则 → 校验 → 落盘 → 驱动调度 | `Scheduler::create` |
| ② 引擎定时执行 | 单定时器 + 全量扫描，永不漏任务 | `ScheduleDriver::scan_due` |
| ③ 任务投递 | 解析发生点、分组、预定会话、注入定时消息 | `fire_group` / `ensure_target` |
| ④ 投递后接受 | `user/message` 事件落盘确认，逐任务记回执并推进 | `SessionQueue` / `acknowledge` |
| ⑤ 执行结果反馈 | 以"会话回到空闲"为完成信号，释放槽位 | `end_turn` / `release_slot` |
| ⑥ 会话内展示与操作 | 会话页头/行标记/轮次卡片展示关联任务，详情面板就地管理 | GUI 会话视图（任务目录快照） |
| ⑦ 崩溃恢复 | 补投错过的触发、重建未完成投递、复用预定会话 | `catch_up` / `restore_inflight` |

## 1.3 必须先建立的两条核心语义

1. **投递回执 ≠ 模型执行完成**。任务持久化的 `last_receipt` / `delivery_log`
   只证明"消息已作为 `user/message` 事件写入目标会话的日志"，不记录模型是否执行、
   结果如何。
2. **调度器是"投递器"不是"执行器"**。它不解析执行结果，不把执行结果回写进任务；
   任务的下一次触发完全由定时规则决定。

这两条决定了整个系统的复杂度边界：调度器只需要管理"何时投、投到哪、投没投成功"，
而把"执行了什么、结果怎样"完全交给会话。

# 第二部分：分步设计详解

## 步骤 ① 任务创建

### 设计是什么

1. **入口（两类调用方，单一管理 API）**：
   - **模型**：调用 `tool:schedule` 的四个工具之一（`schedule_create` /
     `schedule_list` / `schedule_view` / `schedule_edit`），工具内部调用
     `Scheduler::create`。委托子代理被拒绝调用（嵌套层数 > 0 直接拒绝——与其它
     管理工具一致）。
   - **人工（GUI）**：侧边栏的"定时任务"面板通过 host 命令通道调用同一个
     `Scheduler` 的管理方法，**不经过工具层**；新建任务的默认入口是面板上的
     "＋"按钮——跳转到新对话、由模型通过工具创建（见"侧边栏定时任务列表与详情页"）。
   - 两条路径**最终汇聚到同一个底层服务方法**：校验、落盘、调度行为完全一致，
     不存在"人工建的任务和模型建的任务长得不一样"的问题。
2. **纯函数校验**：`schedule::rule` 把模型输入解析成 5 种规则之一
   （`cron` / `once` / `interval` / `daily` / `weekly`）的冻结记录，并做严格校验：
   `title` 必填且 ≤120 字符、`interval` 的步长 ≥ 60 秒、目标时刻必须严格在未来、
   时区必须是规范 IANA 名、`cron` 表达式必须规范化。`cron` 规则直接复用 ADR-0059
   的 `CronSpec`；其余规则新增纯函数解析器。
3. **目标校验（只读，不激活会话）**：验证目标会话（任务）存在性。停靠
   （parked）/ 休眠（dormant）会话允许投递（按需激活）；已删除/不存在的任务拒绝；
   `new` / `new_once` 目标要求存在会话创建能力。
4. **落盘**：任务存储 `put`（JSON 文件 `schedule/tasks.json`），任务状态为
   `active`，初始化空的 `delivery_log`。
5. **驱动调度**：`put` 之后 `kick()`，定时器立即重算指向新任务的最近触发点；
   随后向 `stakeholders` 中已加载的会话异步广播 `[SCHEDULED TASK CHANGE]` 通知
   （不阻塞创建返回）。
6. **返回**：把任务呈现给调用方（模型或 GUI），含下次触发时刻的 UTC 与本地时间。

### 为什么这样设计

- **校验收敛到 domain 纯函数**：规则解析、规范化、时间算术全部无副作用、无 I/O，
  可单元测试（延续 `schedule.rs` 的"自由时钟"风格——wall clock 作为参数传入，测试
  用假时钟），且保证"同一个输入在工具侧与 GUI 侧看到一致语义"。
- **单一管理 API**：工具层（模型入口）与 host 命令（GUI 入口）只是两种调用面，
  底层只有一个 `Scheduler`——任务模型、校验语义、存储格式只有一份。
- **创建不激活会话**：定时任务是 Host 级资源，创建它不该唤醒任何会话（否则"设个
  闹钟"会触发一堆模型回合）。
- **任务不属于会话**：任何会话都可以查看/管理任意任务，投递目标只是任务的一个
  字段——这支持"在一个会话里给另一个会话设任务"的用法。
- **先落盘再驱动**：任务必须先持久化再开始调度，否则进程崩溃时"已触发但没落盘"
  的任务会丢失。

## 步骤 ② 引擎定时执行

### 设计是什么

`ScheduleDriver` 挂在现有引擎线程（独立 OS 线程 + 单线程 tokio runtime）上，
用**一个**定时器调度**所有**任务：

1. **`kick()`**：任意变更（创建/编辑/删除/投递完成）后请求一次调度。若已有扫描
   循环在跑，只合并请求标志；否则启动 `while(requested)` 循环，每轮在引擎命令
   通道的 FIFO 内执行 `scan_due()`——**与管理的写操作串行化**。
2. **`scan_due()` 全量扫描**：找出所有到期任务——`status == active` 且
   `next_fire_at <= now` 且不在 `inflight` 集合 且已过最小投递间隔
   （`rearm_at`）。
3. **只设一个定时器**：从所有 active 任务中取最近的未来触发点 `next`，
   `tokio::time::sleep_until(next)`。定时器跟随引擎线程生命周期——引擎退出即进程
   退出，任务定义在磁盘上，下次启动恢复（见步骤 ⑦）。
4. **到点自查**：定时器到点后清除自身、再次 `kick()` → 重新扫描 → 重设下一个
   定时器。**即使中途没有任何事件，也绝不漏任务**。

### 为什么这样设计

- **单定时器 + 全量扫描**：复杂度从"每任务一个定时器"降到"一个定时器 + O(N)
  扫描"。任务数几千个也只有一个 tokio 定时器，句柄开销可控。代价是每次唤醒都要
  扫全表——但扫描是纯内存操作，毫秒级。
- **事件驱动 + 到点自查双保险**：事件驱动保证"新任务创建后定时器立即对准它"；
  到点自查保证"即使事件丢失（如系统休眠后唤醒），醒来也重新计算"。二者互补，杜绝
  漏任务。
- **FIFO 串行化**：投递与编辑/删除不能并发（否则出现"投递一半任务被删"的竞态），
  统一在引擎命令通道内排队。
- **定时器不阻止退出**：引擎线程的生命周期就是进程生命周期，定时器自然随之结束，
  没有额外的退出句柄问题。
- **投递串行、执行并发**：`scan_due()` 投递各组是串行的，但投递只等消息落盘、
  **不等模型执行**；投递后模型回合在后台异步运行（与现有 `run_turn` 的
  `tokio::spawn` 模型一致）。单线程 tokio runtime 下，等待 I/O（模型 API、工具、
  磁盘）不占线程，多个会话的回合交错并发——定时任务再多也不"排队"；`inflight`
  槽位只防同一任务/会话重复，**不限制跨会话并发**。真正的排队只发生在外部限流
  （模型 API 速率/配额）或 CPU 密集计算时。

## 步骤 ③ 任务投递

### 设计是什么

到期任务进入投递管线（`fire_group`）：

1. **分组（`group_for_session`）**：**只有目标会话 id 完全相同**的任务才合并——
   投给**同一固定会话**的多个 recurring 任务组成一个投递组；**不同会话的任务绝不
   合并**，各自单独投递；`once` 一次性任务与 `new` / `new_once` 目标也单独投递。
2. **发生点解析（`latest_occurrence`）**：循环任务**只取最新一次**发生点（纯
   算术/日历计算，不枚举积压）。这正是 ADR-0059 `recover()` 的"missed 只记录不
   重放"语义的推广。
3. **目标解析（`ensure_target`）**：
   - `session`：向既有任务激活投递（休眠会话按需激活）；
   - `new_once`：首次投递创建保留会话，之后复用；
   - `new`：**先落盘 `reserved_session_id` 预定会话 id，再创建该会话**（用预定 id
     创建任务，随后用任务标题命名）。
4. **投递（`deliver`）**：`SessionQueue::submit` → `inbox.followup(message)`，消息
   带 `source: schedule` 标记，正文为固定 framing（`[SCHEDULED TASK REMINDER]` 或
   批量 `[SCHEDULED TASK REMINDER BATCH]`，内含 `schedule_id` / `occurrence_at` /
   `prompt`）。投递前把任务 id 放入 `inflight` 集合**占位**，防止扫描循环重复投递。

### 为什么这样设计

- **批量合并**：同一会话多个周期任务同时到期时合并为一条消息——减少对会话的打断
  次数，模型一次唤醒处理多件事；但任务账本仍逐任务独立（见步骤 ④）。
- **latest-only 发生点**：循环任务从不"补发"积压的每期触发，只投递最近错过的一
  次。防止停机多日后重启造成轰炸；也省去枚举历史的所有成本。
- **预定会话先落盘**：`new` 目标先落盘 `reserved_session_id` 再创建，崩溃后重试
  **复用同一会话**而非再建一个。会话 id 由运行时自己生成，不是创建过程生成的。
- **固定 framing**：模型可见的定时消息格式稳定，让模型可靠地知道"这是定时消息、
  属于哪个任务"，而不是把投递内容当用户新指令。
- **占位防重**：`inflight` 集合保证"正在投递/正在执行的任务不会被再次扫描到"，
  是并发安全的闸门。

## 步骤 ④ 投递后接受（持久化确认）

### 设计是什么

0. **投递载体：会话收件箱（瞬态内存双队列）**：定时消息不是进入外部消息队列，而是
   进入目标会话的收件箱——`next-turn`（等待新回合的提示）/ `next-step`（等待下一步
   边界的输入）两个队列（`qcode_core::inbox`）。`followup()` 把消息追加到
   `next-turn` 队尾并唤醒引擎驱动，**本质就是让会话走一次与"用户提问"完全同源的
   完整回合循环**——纯后台执行，无用户参与。执行方式是**同一引擎线程内该会话的
   一次异步回合循环**：既不是子代理（工具拒绝委托子代理），也不是单独线程。注意：
   **队列本身是瞬态内存**（`inbox.rs` 注释明言），消息只在被 turn 认领、追加
   `user/message` 事件后才持久——这正是"投递确认"和崩溃恢复必须落在日志事件而不是
   入队动作上的原因。
1. **等待消息持久（认领 + `user/message` 落盘）**：投递后引擎把消息从 `next-turn`
   认领进回合，并作为 `user/message` 事件追加到会话日志。调度器以此写确认
   （日志写句柄返回）作为完成判据——确认消息已在会话里，才继续推进。
2. **逐任务记回执 + 推进（`acknowledge`）**：对投递组里**每个任务**各自确认：
   - 写回执：`occurrence_at`（对应哪个发生点）、`delivered_at`、`messageId`（共享
     同一条消息）、`target_session_id`；
   - 一次性任务收尾为 `ended`；循环任务把 `next_fire_at` 推进到下一次；
   - 历史回执**裁剪保留**：默认只留最近 30 天、最多 200 条，超出的丢弃并标记
     `earlierRecordsPruned`。
3. **失败路径**：任一任务确认失败 → 该任务保持到期状态留在存储，记录失败日志，
   等下一次 `kick` 再试；**没有通用重试循环**。

### 为什么这样设计

- **以"日志事件确认"为完成判据**：`user/message` 事件写入会话日志是持久的、原子的
  边界——"消息一定在会话里了"。以此为分界推进任务，保证推进不会早于投递成功。
- **回执 ≠ 执行完成**：投递后模型可能失败、中断、拖延，都不影响任务推进——调度器
  不等模型。这也是它作为"投递器"的核心体现。
- **逐任务记账**：批量投递只是一条消息，但每个任务的"下次触发时间"和"投递历史"
  独立——A 和 B 在存储里各算各的账。
- **裁剪保留**：投递历史只服务"崩溃去重 + 用户查询"两个目的，不需要无限保留；
  裁剪保证任务记录不会随投递次数无限膨胀。
- **不自动重试**：自动重试会把一次失败放大成定时轰炸；保留任务 + 报告失败，由
  下一次调度自然再试，行为可预期。

## 步骤 ⑤ 执行结果反馈

### 设计是什么

投递成功、消息进入收件箱之后，调度器只消费**两个不携带内容的信号**——执行结果
内容永不回传：

1. **信号①——接受完成（日志落盘确认）**：消息写入会话日志后确认。调度器据此
   **推进任务记账**（写回执、推进下次触发）。
2. **信号②——执行完成（会话回到空闲）**：会话空闲时（`end_turn` → `slot.running`
   置回 false，即现有 `poll` 的 turn 边界），把该投递组所有已提交任务从
   `inflight` 释放 → `kick()` 重算定时器。调度器据此**释放槽位**，允许下一次投递。
3. **失败路径**：先释放未确认的槽位，已确认的等会话空闲统一释放。

模型视角下，任务在 `inflight` 期间呈现为 `inflight: true`，并提供 `rearm_at`
（下一次可投递的时刻）。

**"投递合并、执行合并、记账拆分"**：批量合并的任务由会话**一个回合一起执行**
（一条消息进队列、一次唤醒、模型一次性看到全部 prompt），但每个任务在存储里
**各自独立记账**（各自回执、各自推进下次触发），释放时机则一起（整会话空闲）。

**防堆积（不会越攒越多）**：同一任务在任何时刻最多只有一条定时消息在等待/执行，
三层机制保证：① `inflight` 槽位——执行中扫描跳过，绝不重复投；② `rearm_at`
最小投递间隔——空闲后也要等间隔才能再投；③ latest-only——即便阻塞期间错过多次，
只补最近一次发生点。

### 为什么这样设计

- **用"会话空闲"代替"模型回复完成"**：`end_turn` 是会话生命周期提供的稳定信号，
  比解析模型回复更简单可靠，也不依赖模型输出的具体内容。
- **槽位是并发闸门**：`inflight` 集合同时服务于"防重复投递"与"latest-only 等待
  语义"——会话还在处理上一次投递时，下一次触发不会投，而是等空闲后只投最新一次。
- **反馈通道只有信号、没有内容**：调度器不把模型回复接回来解析。回复作为普通消息
  留在会话历史，属于会话自己的内容——所以执行结果不回传，调度器"投完即放手"。

## 步骤 ⑥ 会话内的定时任务展示与操作（GUI）

### 设计是什么

定时任务不只是侧边栏"定时任务"面板里的冷数据；**在它所牵涉的会话里，也要有一个看得见、能操作的展示框**。会话视图内与任务相关的一切展示/操作，共用同一个任务目录快照作为数据源（与侧边栏面板一致），任何修改都走同一回执通道、确认后再发起权威读取，避免各处展示不一致。

**三处展示入口（同一个数据源）**：

1. **会话页头时钟标记**：会话与至少一个 `active` 任务关联（作为投递目标，或出现在其 `stakeholders` 中）时，会话页头显示下次运行时刻的时钟标记；悬停弹出该会话的关联任务列表——单个任务直接打开展开详情，多个任务弹出列表。会话空闲、未结束且仍有 `active` 关联任务时，标记持续保留。
2. **轮次尾部任务卡片**：`schedule_create` / `schedule_edit` 工具调用后，在轮次末尾渲染一张任务卡片，显示标题、重复规则的可读描述和"打开"操作。卡片数据来自权威目录读取；之后对任务的修改/删除会同步反映到卡片上。
3. **侧栏会话行标记 + 悬浮**：会话行保留同样的时钟标记，悬浮显示关联任务列表（下次运行时间 + 标题）。

**下次运行时间的显示规则**：取计划发生时间（`next_fire_at`）与调度器最早允许投递时刻（`rearm_at`）中**较晚的一项**——避免显示一个"到点却还不能投"的矛盾时间。

**任务详情 / 操作面板**：

- 展示：标题、指令、规则的可读描述、下次运行时刻、状态（`active` / `paused` / `ended`）、最近一次投递回执；
- 操作：**暂停/恢复**（生命周期状态切换）、**立即执行**（手动补一次投递）、**编辑**、**删除**（需确认；删除任务但保留会话与已投递的消息）、**任务运行记录**（投递历史，分页查看，每条显示投递时间与已保存指令，并明确标注"回执确认收件箱投递，不代表模型执行成功"）；
- **投递中冻结编辑**：任务处于 `inflight`（已投递、排队或执行中）时，禁用编辑/保存/暂停恢复/立即执行/删除，提示"已排队或执行中，请在会话中管理"，详情底部提供会话入口；
- **立即执行受 `rearm_at` 约束**：最小投递间隔未满时禁用该操作，并给出可以立即执行的具体时刻；调度器以"投递等待中"拒绝的立即执行显示为状态提示而非错误；
- **编辑冲突处理**：未保存的编辑草稿在切换任务/离开页面时保留；存储版本被外部修改（如模型并发编辑）时，提供"保留修改并复核"（把改过的字段组应用到最新版本）与"放弃"两种选择；
- **空态**：会话没有任何关联任务时，显示空态插图与"新建定时任务"入口——点击后同样
  跳转到新对话并预填创建提示（提示中说明目标为当前会话）。

**与会话无关的全局入口保持分离**：侧边栏的"定时任务"面板面向**全部**任务（不选择、
不激活会话）；会话内的展示框只面向"与这个会话相关"的任务。两个入口都指向同一个
详情/运行记录页；新建统一走"新对话预填提示"路径。

### 为什么这样设计

- **任务出现在它影响的地方**：定时任务"最该被看见"的位置是它的目标/牵涉会话里——用户在一个会话里就能知道"这个会话接下来会被谁、在何时打扰"，并就地管理，无需跳去全局页面。
- **单一数据源**：页头、行标记、轮次卡片、详情面板全部订阅同一个任务目录快照，消除"多处展示不一致"。
- **读取不激活会话**：展示与读取都不唤醒会话，延续"创建不激活会话"的语义——看任务不等于触发模型回合。
- **诚实标注回执**：任务运行记录明确"确认收件箱投递，不代表模型执行成功"，与核心语义一致，避免用户把"已投递"误读为"已执行"。
- **投递中冻结**：批量消息可能同时携带多个任务的投递，对单个任务取消/编辑会产生"消息还在、任务却已改"的不一致；因此投递/执行期间整体冻结，统一交给会话内管理。
- **时间显示取较晚者**：`next_fire_at` 与 `rearm_at` 共同决定"实际何时投"，显示较晚者才不会出现"显示该投了却还没投"的困惑。

## 步骤 ⑦ 崩溃恢复

### 设计是什么

崩溃/重启后，三条机制协同恢复：

1. **启动 catch-up（`catch_up`，补投错过的触发）**：引擎启动即 `kick()`，会话激活
   能力就绪后再 `kick()`（补投错过的任务）。`scan_due()` 扫描时发现
   `next_fire_at <= now` 的任务**立即补投**，循环任务按当前时刻推进发生点——
   **只补投最近一次**。
2. **重建未完成的投递（`restore_inflight`）**：重启后，对每个有 `last_receipt`
   的任务按 `messageId` 查目标会话日志：**若日志中还没有对应的 `user/message`
   事件**，说明"上次投了但还没认领/没落盘"——把任务重新挂回 `inflight` 槽位并
   重新 `followup` 同一消息，**避免丢失**；同一条批量消息的其他任务通过共享
   `messageId` 一并恢复。**若日志中已有该事件**，则投递已确认，正常推进。
3. **预定会话复用（`reserved_session_id`）**：`new` 目标投递前已把预定会话 id
   落盘；崩溃后重试读取该值，**复用同一个会话**，而不是再创建一个。

同时如实声明局限：

- 投递与推进**非原子**：崩溃窗口内可能重复投递（工具描述明示 "Delivery can repeat
  after a crash"）；
- 正在执行的模型回合随进程退出而中断，**不会**在重启后继续跑（回合本身不持久化，
  只有已落盘的 `user/message` 事件能确认投递）。

**正常退出 vs 崩溃重启的细分语义**：

| 退出时刻 | 下次启动行为 |
|---|---|
| 投递已认领、`user/message` 事件已落盘但回合没跑完 | 日志中有该 `messageId` 事件 → 不重投；会话恢复时从事件重放回合，**从消息起点**重来（非断点续传——推理到一半的状态不持久化） |
| 消息已 followup 但尚未被认领落盘 | 任务无回执 → 按到期补投（窗口内可能重复投递） |
| 任务还没到触发点 / 还没投 | 启动 catch-up 按 `next_fire_at` 补投最近一次 |
| 任务已处理完（事件已落盘） | 日志中有该 `messageId` 事件 → 不重复，正常推进 |

**执行一半的回合：自动修复，不是断点续跑**。消息已被 claim、回合执行到一半崩溃时：
中间事件**不回退**（会话日志是 append-only 事件溯源），但回合循环是进程内 async、
崩溃即死、无执行指针。会话恢复时扫描日志尾部（与现有 `resume` 的日志重放一致），
发现未完成回合则自动追加合成关闭事件：悬空的工具调用补错误回执（"结果未知，仅
只读/幂等可重试，否则先验证外部状态或问用户"）+ `step/end` + `turn/end(reason:
interrupted)`——半截回合被**正式关闭**，日志恢复平衡。调度器视角：日志中没有该
`messageId` 的 `user/message` 事件 → 任务按到期补投；已存在 → 不重投、任务已推进。

**槽位是内存态，崩溃即清零**：`inflight` 是引擎线程私有的内存集合，不是持久化
任务状态（任务状态在存储里）。崩溃 → 进程死 → 槽位清零，**不存在"僵尸占位"**；
重启后由 `restore_inflight` 按日志中的 `user/message` 事件重新判定哪些投递确实
发生过。正常运行时槽位在会话空闲（必然到达）时释放。

### 为什么这样设计

- **以日志事件为事实源去重**：恢复时"查目标会话日志里有没有这个 `messageId` 的
  `user/message` 事件"——这是唯一能区分"投过没投过"的持久依据，因为任务侧只记了
  回执、没有执行状态。
- **预定先落盘**：`reserved_session_id` 把"选会话"从"建会话"中拆出并先持久化，
  把崩溃窗口从"创建会话之后"前移到"落盘之前"，大幅降低重复建会话的概率。
- **latest-only 补投**：停机多期只补最近一次，避免重启后瞬间轰炸。
- **优雅退出与恢复衔接**：退出会**排空已接受的投递**再关存储，所以正常退出时窗口
  更小；真正的崩溃才依赖上述恢复。

# 附：生命周期与数据模型

## 启动 / 退出

| 阶段 | 行为 |
|---|---|
| 启动 | `kick()` + 会话激活能力就绪后再 `kick()`（补投错过的）；同时把现有 `[schedules]` 声明式条目导入为 active 任务（一次性迁移，行为不变） |
| 退出 | 置停止标志 → 清定时器、排空已接受投递 → 排空通知队列 → 关存储 |
| 变更通知 | 任务被外部修改时，向 `stakeholders` 中已加载的会话注入 `[SCHEDULED TASK CHANGE]`（非唤醒） |

## 持久化数据模型

`schedule/tasks.json`，每个任务一个对象：

| 字段 | 内容 | 关键语义 |
|---|---|---|
| `rule` | 5 种定时规则之一（冻结对象） | 权威定时规则 + `next_fire_at`（下一次触发点） |
| `status` | `active` / `paused` / `ended` | 任务状态机 |
| `target` | `session` / `new_once` / `new` | 投递去向 |
| `overlap` | `queue` / `skip` | 会话忙时行为（沿用 ADR-0059 语义） |
| `approval_timeout` | `Option<Duration>` | 定时回合的审批超时，超时自动拒绝 |
| `stakeholders` | 牵涉会话集合（创建/操作会话 + 非 `new` 目标会话，只增不减） | 变更通知路由表 |
| `last_receipt` / `delivery_log` | 投递回执（`occurrence_at` / `delivered_at` / `messageId` / `target_session_id`），默认裁剪保留 30 天 / 200 条 | 回执 ≠ 执行完成 |
| `reserved_session_id` | `new` 投递前先落盘，确认后清除 | 崩溃时复用预定会话 |

## 与现有机制的关系（落地映射）

| 现有机制 | 本设计的位置 |
|---|---|
| `qcode_core::schedule`（cron 解析、`tick/recover/advance` 纯函数、`ScheduleState`） | 保留为规则的子集与语义基础；`cron` 规则直接复用 `CronSpec`；`recover` 的 missed 语义即 latest-only 的雏形 |
| `[schedules.<name>]` 配置条目（ADR-0059） | 声明式旧入口：启动时导入为 `active` 任务，行为不变（调度时钟、overlap、审批超时、`schedule_hints` 全部保留） |
| 引擎线程 + 单线程 tokio runtime（`runtime::spawn`） | `ScheduleDriver` 挂在该线程上；单定时器用 `tokio::time::sleep_until` |
| 会话收件箱 `SessionQueue` / `Inbox`（`next-turn` / `next-step` 瞬态内存双队列；消息被 turn 认领后以 `user/message` 事件持久） | 投递载体；崩溃恢复的事实源是日志中的 `user/message` 事件 |
| `SessionHost` 槽位（cancel token + queue + running） | `inflight` 占位与"会话空闲"信号的落地基础 |
| 会话日志（append-only JSONL + `SessionLock`） | 投递确认边界；中断回合由日志重放 + 合成关闭事件修复 |
| 审批队列 + `approval_timeout` | 定时回合沿用，超时自动拒绝 |
| GUI `poll`（ADR-0058 常驻 drain） | 消费 `inflight` 释放后的重绘与 `schedule_hints` 展示 |
| 会话视图（页头、侧栏行、轮次尾部） | 关联任务的时钟标记、悬浮列表、轮次尾部任务卡片；任务详情面板与就地操作 |
| GUI 侧边栏（新增） | "定时任务"面板：全量列表 + 状态；新建入口（"＋"在对话中创建 / "⋮"菜单含手动创建表单）；详情 + 运行记录页承载编辑表单与投递历史 |
| `qcode-tools` 工具注册表 | 新增 `schedule_create/list/view/edit` 工具，拒绝子代理调用 |

## 侧边栏定时任务列表与详情页

**入口与结构**：定时任务**没有独立的全局列表页**——整个列表常驻在**侧边栏**。
侧边栏新增"定时任务"面板，展示**全部**定时任务及其状态；不选择、不激活任何会话；
与会话内的展示框（步骤⑥）共用同一个任务目录快照与同一套回执通道。

**列表（侧边栏面板）**

- 每个任务显示：标题、规则的可读描述、下次运行时刻（`next_fire_at` 与 `rearm_at`
  取较晚者）、状态（`active` / `paused` / `ended`）、最近一次投递回执；
- 提供状态分组或筛选（已开启 / 已暂停 / 已结束 / 全部，默认已开启）；
- 面板顶部"＋"按钮与它旁边的"⋮"按钮 = 新建入口（见下）。

**新建（两个入口）**

- **在对话中创建（"＋"按钮）**：点击"＋"→ **跳转到一个新对话（新建会话）**，并在
  输入框中预填提示：`请根据需求创建一个定时任务。\n`，作为未发送的草稿（另起一行）；
  用户补充需求后发送，由模型通过 `schedule_create` 等工具创建任务。若复用空白会话，
  预填提示追加到原草稿末尾，保留原有文本、行内引用与附件。
- **"⋮"按钮（"＋"旁的三个点）**：点击展开菜单，含两个选项：
  - **在对话中创建**：与"＋"行为完全一致（跳转新对话 + 预填提示）；
  - **手动创建**：弹出创建页面（表单），用户直接填写任务信息——**名称、内容、周期**
    等。字段与详情页编辑表单一致：名称（≤120 字符）、内容（指令 / prompt）、周期
    （5 种规则的友好编辑器：`once` 日期+时间、`interval` 步长 ≥60 秒、
    `daily` / `weekly` 钟表时间、`cron` 自定义输入框复用 `CronSpec` 校验）、目标
    （既有会话 / 新建并复用 / 每次新建）、`overlap`、审批超时、时区。校验与保存规则
    一致：只有字段有效且有实际修改才能保存（保存只发送变更字段 + 版本号）；无效 /
    空输入保留草稿并说明需修改的字段；宿主在保存时做最终校验；失败时保留表单与已填
    内容。手动创建**只保存任务**，不启动回合、不发送指令。
- 两个入口汇聚到同一个 `Scheduler::create`——任务模型、校验语义、存储格式一致。

**任务详情 + 运行记录页**

- 点击列表中的某个任务 → 进入"任务详情 + 运行记录"页：
  - 详情区：标题、指令、规则的可读描述、目标、`overlap`、审批超时、状态、
    下次运行时刻、最近一次投递回执；
  - 操作：暂停/恢复、立即执行、编辑、删除（需确认；删除任务但保留会话与已投递的
    消息）；
  - 运行记录（投递历史）：分页（每页 20 条，从新到旧），每条显示投递发生时刻与
    已保存指令，长指令可展开 / 收起，回执中实际执行会话可用时提供入口；明确标注
    "回执确认收件箱投递，不代表模型执行成功"；仅在最后一页且确认裁剪后显示清理
    提示，并给出当前保留规则说明。
- **编辑表单（承载在详情页）**：
  - 字段：标题（≤120 字符）、指令（prompt）、规则、目标（既有会话 / 新建并复用 /
    每次新建）、`overlap`、审批超时、时区；
  - 规则编辑器：5 种规则各自给出友好控件——`once` 日期+时间、`interval` 步长
    （≥60 秒）、`daily` / `weekly` 钟表时间、`cron` 自定义输入框（复用 `CronSpec`
    校验）；时区选择器用 IANA 清单（系统时区兜底，未列入清单的已存别名保留）；
  - 校验与保存：只有字段有效且有实际修改才能保存（保存只发送变更字段 + 版本号）；
    无效 / 空输入保留草稿并说明需修改的字段；宿主在保存时做最终校验；保存成功后
    字段保持可编辑；
  - 目标选择："新建并复用"默认选中；已有目标的任务显示"当前关联会话"，编辑时保留
    原目标，除非用户主动切换；`new` 目标在首次投递前显示"待创建"，之后显示"最近
    运行会话"入口（可导航）。
- **草稿与冲突（版本化编辑）**：未保存草稿在切换任务 / 离开页面时保留（侧边栏详情
  与会话内展示框的草稿各自独立）；存储版本被外部修改（如模型并发编辑）时：未修改
  的表单跟随新版本；已修改的保留草稿并禁用保存，提供"保留修改并复核"（把改过的
  字段组应用到最新版本，供保存前复核）与"放弃"；迟到响应不改变其他任务详情。
- **投递中冻结**：任务处于 `inflight`（已投递、排队或执行中）时禁用字段、保存、
  暂停/恢复、立即执行和删除，提示"已排队或执行中，请在会话中管理"，详情底部提供
  会话入口；立即执行受 `rearm_at` 约束，未满间隔禁用并给出可执行时刻；调度器以
  "投递等待中"拒绝时显示为状态提示而非错误。

**与模型工具的协作**

- 侧边栏与详情页读取不激活会话；模型并发修改任务时，冲突反馈沿用上文的复核流程；
- 列表、详情、会话悬浮各处显示的下次运行时间统一取 `next_fire_at` 与 `rearm_at`
  中较晚者。

### 为什么这样设计

- **列表常驻侧边栏**：定时任务是一等公民，随时可见、可管理，不必打开设置窗口；
  侧边栏空间天然适合"常驻 + 可折叠"的全量列表。
- **新建走新对话**：让模型参与任务定义——自然语言直接生成规则，比人工填表单更
  贴合"任务由模型创建"的本项目语义；人工入口简化为一个预填提示的按钮。
- **详情 + 运行记录一页闭环**：任务的一切（信息、操作、历史）集中在点击进入的一
  页里，路径短、状态可追踪。
- **版本化编辑 / 冻结编辑 / 诚实标注回执**：动机与步骤⑥一致——人工与模型并发
  编辑、投递中批量消息不可拆分、回执 ≠ 执行。

## 设计原则总结

1. **任务 Host 级、与会话解耦**：任务不属于任何会话，投递目标只是字段。
2. **投递器而非执行器**：回执不记执行、结果不解析，职责边界清晰。
3. **简单调度器**：单定时器 + 全量扫描 + 事件驱动 + 到点自查，杜绝漏任务且实现
   极简。
4. **latest-only**：循环任务只补最近一次，防积压防轰炸。
5. **以持久边界定语义**：`user/message` 事件落盘为推进分界、日志事件为崩溃恢复的
   事实源。
6. **写前落盘**：`reserved_session_id` 先落盘再执行，缩小崩溃窗口。
7. **非原子写入被如实声明**：可能重复投递，作为明确接受的风险。
