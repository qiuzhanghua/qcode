## 1. 结论摘要

1. **现状不是「没做 i18n」，而是「做了两种、缺第三种状态」**：`qc --help` 全英文、
   `qc schedule list` 全中文、GUI 全中文（§2.1）。
2. **有一个已经存在的 bug**：`qcode-gui` 从未调用 `set_locale`，框架停在 `en`，
   所以中文 GUI 的剪贴板菜单写着 `Copy`。修它不是新功能，是还债（§2.4）。
3. **翻译层只有一个**：钉 `rust-i18n 4.2.x`，与 `gpui-component` 同一份。写 `3.x`
   会链入两个 `CURRENT_LOCALE`，语言静默分叉（ADR-0105 §1）。
4. **生产代码里待处理的中文字符串 554 条**（crate 内去重；跨 crate 合并后 531），
   其中 GUI 占 393 条 —— **71% 在一个 crate 里**（§2.2）。
5. **「432 处断言要改」是错的**。实测只有 **≈93 处**真正断言中文文案，另 154 行中文
   只是 `assert!` 的失败诊断信息，与语言无关（§2.3）。
6. **四类字符串，处置完全不同**：UI 文案要翻；prompt 永不翻；工具返回值要翻（但记代价）；
   测试数据永不翻（§2.3）。**混淆它们是本次最大的估算错误来源**。
7. **4.x 的 `t!` 绑定调用方 crate**，所以不能用「每 crate 一份 yml」以外的宏方式共享
   locales；我们选「单 crate 持 locales + 函数访问器」（§4.2）。

## 2. 现状盘点

### 2.1 语言现状（三个面，三种语言）

| 面 | 现状 | 依据 |
|---|---|---|
| `qc --help` / 子命令帮助 | **几乎全英文，但 `qc daemon --help` 中英混排** | clap derive 的 `///` 注释放英文；`cli.rs:363-366,395` 的 `///` 是中文，会被 clap 当作 `about`/`long_about` 输出 |
| 运行时输出（`qc schedule list`、`qc logs` 等） | **全中文** | `commands/schedule.rs`、`daemon.rs` 等 |
| GUI / TUI | **全中文** | 554 条里 GUI 393、TUI 8 |

一个英文用户开箱看到的顺序是：英文帮助 → 中文列表 → 中文界面。要统一，只能往

### 2.3 四类字符串的分类学（本节是本文最重要的部分）

我把「432 处断言」一开始当成一笔成本，实际拆开后是完全不同的四件事：

| 类别 | 数量 | 处置 | 为什么 |
|---|---|---|---|
| **A. UI 文案** | 554 − prompt − 工具 | **翻** | 就是本文要干的事 |
| **B. prompt（发给模型的指令）** | **6**（`title.rs` 2、`turn.rs` 3、`question.rs` 1） | **改成英文，不进翻译表** | 翻 = 改模型行为 + 毁 prompt 缓存 + 让 eval 基线漂 |
| **C. 工具返回值与 spec** | 58 | **翻**（ADR-0105 §5） | 它是用户看的结果面；代价见下 |
| **D. 测试数据 / 失败诊断** | 432 中的大多数 | **永不翻** | 不面向用户；诊断信息与语言无关 |

**B 类首盘漏计了 4 条**：原来只数了 `title.rs` 的 2 条，实际 `turn.rs` 的
`CONTINUE_PROMPT` / `WRAP_UP_PROMPT` / `HAND_OFF_PROMPT` 和 `question.rs`
`pending_result()` 里那个 JSON 载荷同样是发给模型的指令。数量从 2 改成 6，处置从
「保留中文」改成「写成英文」——理由见 §10.9。

**D 类为什么不算成本**，实测拆解：

| 类别 | 数量 | 例子 |
|---|---|---|
| 中文只是 `assert!` 的**失败诊断信息** | **154 行** | `assert_eq!(report.fired, 0, "第一拍不投递任何东西")` |
| `assert_eq!` 的**期望值**是中文串 | **22 处** | `assert_eq!(title, "中文标题")` |
| `.contains/starts_with/ends_with("中文")` | **71 处** | `assert!(tip.contains("点一下"))` |
| **真正依赖中文文案的断言** | **≈93 处** | 上两行之和 |

第一行那 154 处里，中文是**给失败时的人看的**，被断言的是 `0`、`1`、长度、布尔值 ——
无论界面说什么语言，它们永远成立。

**C 类的代价如实记**（ADR-0105 §5 已记，这里留一份可检索）：

1. 同一工具调用在不同语言下字节不同 → **语言切换那一次**缓存失效（同一语言内稳定）；
2. eval 基线要按语言各记一套；
3. 历史会话里已存的中文不回改。

**B 类的具体位置**：

| 位置 | 内容 | 依据 |
|---|---|---|
| `qcode-core/src/title.rs` `title_system_prompt()` | 会话标题的系统指令 | 函数注释：*"the model owns the language choice"* |
| `qcode-core/src/title.rs` `frame_title_input()` | JSON 框架输入 | 同上 |

`qcode-core/src/engine/mod.rs` 的 `system_prompt()` 本身是**全英文（0 条中文）**，
P0 之后也不该有中文。

`qcode-core/src/engine/turn.rs` 的 4 条中文（`本次没有改动文件`、`调用了 {} 次工具` …）
**不是 prompt，是 run 模式的用户可见摘要**，属 §2.3 的 A 类，随 UI 语言翻译。

| 依赖 | 版本 | 说明 |
|---|---|---|


`crate::` —— 绑定**调用方**。这就是 §4.2 那条决策的唯一依据。

## 3. 硬约束与不变量

1. **`QCODE_LANG=en` 下的输出必须与现状逐字节一致**（除 §2.4 的 bug 修复外）。
   这是唯一的安全网，也是 golden 的基线。
2. **机器消费的输出绝不翻译**：`--version`、JSON、id、路径、命令名、参数名、
   环境变量名、cron 表达式、模型 ID。
3. **日志不翻译**（现状已合规，0 条中文，不要「顺手统一」）。
4. **prompt 不翻译**（§2.3 B 类）。
5. **测试进程钉 `zh-CN`**，且测试内**不得**临时 `set_locale`（进程级 `AtomicStr`，
   并行污染）。
6. **不新增翻译库**。只有一个 `rust-i18n`，且是 4.2.x。
7. **CLI 不两次 parse**。`init()` 必须在 `try_parse()` 之前调用一次。
8. 一个提交内**同一面要么全翻、要么不动**。

## 4. 接口设计

### 4.1 新建叶子 crate `qcode-i18n`

```
crates/qcode-i18n/
├── Cargo.toml          # rust-i18n 4.2, sys-locale 0.3
├── locales/app.yml     # 唯一一份翻译表
└── src/lib.rs
```

**落地清单**（这个仓库不会自动发现新 crate，漏一步就编译不过）：

1. `Cargo.toml` 的 `[workspace] members` **是显式列举，不是 glob** —— 必须手动加
   `"crates/qcode-i18n"`。
2. 新 crate 的 `version` 与其他 crate 对齐（当前 `0.16.0`），依赖写
   `rust-i18n = "4.2"`（**不是 `"3"`**，见 ADR-0105 §1）、`sys-locale = "0.3"`。
3. 需要用到它的 crate 逐个加 path 依赖（既有的写法带版本号，照抄相邻行）。

`src/lib.rs` 的形状：

```rust
rust_i18n::i18n!("locales", fallback = "en");   // 必须在 crate 根

pub const EN: &str = "en";
pub const ZH_CN: &str = "zh-CN";
pub const SUPPORTED: [&str; 2] = [EN, ZH_CN];
pub const DEFAULT: &str = EN;
pub const LANG_ENV: &str = "QCODE_LANG";

/// 归一化；认不出返回 None。见 §4.4。
pub fn normalize(raw: &str) -> Option<&'static str>;

/// 纯决策：显式 > 系统 > DEFAULT。
pub fn decide(explicit: Option<&str>, system: Option<&str>) -> &'static str;

/// 唯一的副作用入口。在 clap 的 try_parse 之前调用一次。
pub fn init(configured: Option<&str>);

/// 无参取值。
pub fn tr(key: &str) -> std::borrow::Cow<'static, str>;

/// 带 %{x} 插值。
pub fn trf(key: &str, args: &[(&str, &str)]) -> String;

pub fn locale() -> String;
pub fn set(locale: &str);       // 归一化后写入
```

### 4.2 为什么是函数访问器而不是 `t!`

**4.x 的 `t!` 绑死调用方 crate**（§2.5）。三条路：

| 方案 | 结论 |
|---|---|
| 每个 crate 自己 `i18n!` + 一份 `locales/` | 10 个 crate → 10 个 yml，翻译要对着 10 个文件干活，key 会漂 |
| 每个 crate `i18n!` 指向同一目录（`../qcode-i18n/locales`） | 同一份表被编进每个二进制；相对路径脆弱，`cargo publish` 会断 |
| **单 crate `i18n!` + `pub fn tr/trf`** | **选它**。一份 yml；代价是丢 `t!` 语法糖，可用 ~10 行 `macro_rules!` 补回 |

`i18n!` 生成的 `_rust_i18n_translate` 是 `pub fn`，所以同 crate 内的薄封装直接可用：

```rust
pub fn tr(key: &str) -> Cow<'static, str> {
    _rust_i18n_translate(&locale(), key)
}
```

如果以后觉得 `qcode_i18n::tr("...")` 太啰嗦，在 `qcode-i18n` 里加：

```rust
#[macro_export]
macro_rules! t {
    ($key:literal) => { $crate::tr($key) };
}
```

这是可选糖，不进 P0 的验收。

### 4.3 接线点（只有四处）

| 位置 | 时机 | 备注 |
|---|---|---|
| `crates/qcode/src/main.rs` | 在 `Cli::parse_from()` **之前**（`main.rs:56`）；P2 起换成 `try_parse_from`，见 §4.5 | clap 帮助文案在解析时求值；`QCODE_LANG` 读不到要落 §4.4 的默认 |
| `crates/qcd/src/main.rs` | 在 `early_exit()` 之后、装配之前 | `qcd --help` 是手写常量，见下 |
| `crates/qcode-gui/src/setup/mod.rs:319/335`、`run.rs:84` | 紧跟 `gpui_kit::init(cx)` | **一次 `set()` 同时覆盖框架与我们的文案** |
| `crates/qcode/src/tui.rs` | 启动时 | TUI 无框架依赖，只需自己的文案 |

**`qcd` 的特殊情况**：它的 `--help` / `--version` 是**手写常量 `HELP`**（为了在任何
初始化之前、也不建 `logs/` 就回答）。所以 `qcd --help` 的汉化不能靠 `init()`，要
单独决定：要么保持英文（它面向脚本与 `qc update`），要么在 `early_exit()` 里读
`QCODE_LANG` 再选常量。**建议保持英文** —— 它和 `--version` 一样是被机器解析的。

**GUI 的重启生效**：README 与本设计都说「改配置后重启生效」。`rust-i18n 4.2.4` 有
`LOCALE_VERSION` 做缓存失效，但**没有观察者**，实时切换要自己加重绘广播（ADR-0105 §9
明确排除）。

### 4.4 语言决策（已冻结，单测全表覆盖）

`normalize(raw)`：

1. `trim`；空 → `None`
2. 按 `['.', '@']` 切掉编码与修饰符（`zh-Hans-CN@euro` → `zh-Hans-CN`）
3. `_` → `-`，转小写
4. 只看**第一个 subtag**：

| 输入首个 subtag | 结果 |
|---|---|
| `c` / `posix` | `en`（Linux CI 的 `LANG=C.UTF-8`） |
| `en` | `en` |
| `zh` | `zh-CN`（繁体也走简体，只有一份译文） |
| 其他（`fr`/`de`/`ja`/`zho`…） | `None` |

**必须覆盖 `zh-Hans-CN`**：这是 macOS `CFLocaleCopyPreferredLanguages` 的真实返回值。
不归一化就 `set_locale` 原样传入，rust-i18n 查不到会**静默 fallback 到英文**，不报错。

`decide(explicit, system)`：

| explicit | system | 结果 |
|---|---|---|
| `Some("en")` | 任何 | `en` |
| `Some("zh-CN")` | 任何 | `zh-CN` |
| `Some("fr")`（认不出） | `Some("zh-Hans-CN")` | `zh-CN`（静默下探，不报错） |
| `Some("")` | `Some("zh-CN")` | `zh-CN`（空串当未设置） |
| `None` | `Some("C.UTF-8")` | `en` |
| `None` | `None` | `en`（`DEFAULT`） |

`init()` 里读 `QCODE_LANG`，否则 `sys_locale::get_locale()`。**只取系统首选**，
不扫描整个优先级列表：首选是法语的用户给他中文更奇怪。

### 4.5 clap 内置标签的收口（P2，唯一需要改 parse 方式的地方）

**这是个真实缺口，先说清楚它为什么绕不过去。** clap 自带的这些字符串**硬编码在
`clap_builder` 里，没有任何公开 API 可配**：

`Usage:` / `Arguments:` / `Options:` / `Commands:` / `Print help` / `Print version` /
`Print this message or the help of the given subcommand(s)` / `error:` / `tip:` /
`For more information, try '--help'.`

而我们自己的 554 条里**没有一条**是它们。所以只做 §4.1 的 `tr()`，`qc --help` 会变成
「中文的 about + 英文的 `Usage:`」—— 比现在更难看的混排。

**唯一的收口点**：clap 把「渲染」和「打印」分开了，且渲染结果是公开的：

```rust
clap::Error::render()      -> StyledStr   // pub
clap::Error::kind()        -> ErrorKind   // pub
clap::Error::exit_code()   -> i32         // pub
clap::Error::use_stderr()  -> bool        // pub，省去自己 match kind 判断流向
```

于是把 `Cli::parse_from(argv)`（`main.rs:56`）换成 `try_parse_from`，拿到 `Err(e)` 后
渲染成文本、过一遍规则表、再打到对应流：

```rust
match Cli::try_parse_from(argv) {
    Ok(cli) => cli,
    Err(e) => {
        let rendered = clap_text::apply(&e.render().to_string());
        let code = e.exit_code();
        if e.use_stderr() { eprint!("{rendered}") } else { print!("{rendered}") }
        std::process::exit(code)
    }
}
```

**时间点**：这是 **P2** 的事，不是 P0。P0 保持 `parse_from` 不变（那时还没有一条翻译，
改了只会让 P0 的 golden 全是噪声）。

**规则表**（照 cot_cli §7.3 的四类形状，不照抄它的 498 行）：行首锚定（节标题）、
子串（`Print help`，它在参数名之后，不在行首）、前包裹（`%{x}`）、双洞包裹
（`%{x}`/`%{y}`，给 `invalid value 'X' for 'Y'` 那种）。

**两条必须记住的坑**（cot_cli 实测过的）：

1. **规则顺序敏感**。`Print help (see more with '--help')` 必须排在裸的 `Print help`
   之前，否则先被短规则截断，留下半句英文。
2. **中文路径会失去颜色**。`StyledStr` 的 `Display` 明确是 colorless，所以
   `render().to_string()` 是纯文本。`en` 路径仍走原生 `print()`，颜色不变——只有中文
   用户看到无色输出。这是接受的取舍；要保色得自己重新着色，属独立改动。

对应验收（ADR-0105）：`QCODE_LANG=zh-CN` 下 `qc --help` **不出现**上列英文标签；
`en` 下逐字节不变。

## 8. 门禁与测试

### 8.1 八道门禁（都进 `make check`）

1. **key 集合相等**：用 `serde_yaml`（已有依赖）解析 `app.yml`，断言 `en` 与 `zh-CN`
   的叶子 key 集合完全相同。缺一条 → 红。
2. **禁止裸中文 UI 字面量**：脚本扫描 UI 层（`crates/qcode-gui`、`qcode-tui`、
   `crates/qcode/src/commands`），命中中文字符串字面量即失败。白名单：
   `qcode-core/src/title.rs`（prompt）、`qcode-tools`（P3 前）、所有测试代码。
   **同一条门禁的英文面**（`no_new_hardcoded_english_ui_text`）：按**位置**抓硬编码
   英文 UI 文案（`.label(` / `.aria_label(` / `group_heading(` / `label:` / `help:` /
   `title:`，`forms.rs` 另加 `=> `，工具结果摘要另加 `ToolOutput::ok(` / `err(` /
   `cancelled(`，CLI 命令输出另加 `println!(` / `eprintln!(`），扫**全部** crate，
   基线 `scripts/i18n-baseline-en.txt` 同样是棘轮。
   两条是一件事的两个方向：只查中文会漏掉整类「英文硬编码」，见 §10.11。

   **有意不收的位置**：`push_str(` / `write!(`。它们是通用字符串拼装，
   `qcode-tools/macos.rs` 用它拼 `sandbox-exec` 的 profile DSL（`(allow file-read*`），
   翻了那条规则沙箱就废了。位置判据在「通用 API」上失效，所以只认
   `ToolOutput::*` 这个唯一构造入口——`run_shell` 的超时/取消也走它（§10.13）。
   `spec(` 与 `ToolError::*` 同样不收：那是发给模型的 schema 与参数诊断，有意保持
   英文。
3. **双语 golden**：`QCODE_LANG=en` 与 `QCODE_LANG=zh-CN` 各跑一遍**整棵命令树**的
   `--help` 与几种典型报错，diff 对基线（现 87 项：43 用例 × 2 语言 + `--version`）。
   用例集合**从二进制自己的 `--help` 递归发现**，不是手写列表。`en` 那份必须零差异。
   另有一条**颜色**检查：主流程固定了 `NO_COLOR=1`（否则 diff 全是转义码），于是
   「en 丢了颜色」在文本基线里完全不可见——实测过能绕过。所以在伪 TTY 下单独抓一次
   `en` 的 stderr，断言它**带**转义码（§10.11）。
4. **引用的 key 必须存在**（`every_referenced_key_exists`）：扫源码里的
   `tr("…")` / `trp("…")` / `_rust_i18n_translate(…, "…")` 字面量。找不到 key 时
   rust-i18n **把 key 原样当文案返回**，界面上才会露出 `<locale>.<key>`。
5. **声明了就要取得到**（`every_key_resolves_at_runtime`）：每个声明的 key 在两种
   语言下都真的能解析。它兜的是「`i18n!` 在宏展开时读 yml，cargo 看不见那次读」
   ——只改 yml 不重编，二进制里还是旧译文。`build.rs` 的 `rerun-if-changed` 治因，
   这条兜果。
6. **声明了就要有人引用**（`every_declared_key_is_referenced`）：孤儿 key 是翻译表
   腐坏的起点（改一条没人用的文案，界面毫无变化）。`cli.cmd.*` 是动态寻址的，
   显式放行，交给门禁 7。
7. **CLI 帮助树可达性**（`crates/qcode/src/cli_i18n_gate.rs`）：`cli.cmd.*` 按命令
   路径拼出来，静态扫描看不见，所以遍历**真实的** `Command` 树双向比对——「声明了
   却查不到」与「查得到却没译文」都要红。
8. **设置页数据表可达性**（`crates/qcode-gui/tests/spec_i18n.rs`）：`forms.rs` 的
   `FIELDS` / `GUI_FIELDS` / `TABLES` 同理（`gui.setup.spec.*`）。除双向覆盖外还查
   「同一张表里列 key 重复」（重复时两行显示同一个名字，没有别的门禁能发现）。

门禁 2 是**机制性防范**：靠人记不住 554 条，靠 grep 能记住。它的已知盲区与门禁 4–7
各自的「为什么必须是它而不是别的」见 §10 的逐批记录。

### 8.2 现有 ≈93 处断言怎么处理

**一行不改。** 测试进程钉 `zh-CN`（ADR-0105 §6）。

实现方式：每个测试二进制启动时钉**一次**，值恒定、幂等，并发无竞争：

```rust
#[cfg(test)]
pub fn pin_for_tests() {
    static ONCE: std::sync::Once = std::sync::Once::new();
    ONCE.call_once(|| set(ZH_CN));
}
```

**禁止**在单个测试里换语言：`rust-i18n` 的 `CURRENT_LOCALE` 是进程级 `AtomicStr`，
并行测试互相污染。确需英文断言的地方用逐调用覆写（`t!(key, locale = "en")` 形态），
不改全局。

**英文路径靠什么保证**：不靠断言，靠 §8.1 的门禁；CLI 帮助另有 §4.5 的两套机制。

### 10.2 与计划的三处偏差

1. **`init` 传 `None`，没有读配置**。计划里 `init(configured)` 收一个配置值，但
   配置加载在 clap 之后（`parse` 才知道 `--config` 在哪），而语言必须在 clap
   **之前**定。要读 `[ui] language` 就得先扫一遍 argv 找 `--config`，那与「不乱
   parse 两次」的纪律相冲突。所以 P0 严格按 ADR-0105 决定 2 只做
   `QCODE_LANG` → 系统 → `en`，签名留好参数，配置层整条留到 P2（§9 第 4 条）。
2. **`app.yml` 落了 2 条 key，不是 0 条**。计划说「0 条翻译」，但没有一条真 key
   就没法证明 `tr` / `trf` / 门禁 1 都在工作。这 2 条是基建的自检样本。
3. **`serde-saphyr` 成了 dev-dependency**。门禁 1 要解析 `app.yml`。选它是因为
   **它已经在 `Cargo.lock` 里**（`rust-i18n-support` 自己的 YAML 解析器），
   所以这条边不新增任何 crate。`cargo deny check licenses/bans/sources` 均绿。

### 10.3 门禁 2 是棘轮，不是白名单

基线 `scripts/i18n-baseline.txt` 记的是**现存全部**裸中文字面量，实测 **547 条**：

| crate | 条数 |
|---|---|
| `qcode-gui` | 393 |
| `qcode-tools` | 57 |
| `qcode-core` | 36 |
| `qcode` | 29 |
| `qcode-kernel` | 18 |
| `qcode-tui` | 8 |
| `qcode-ui-state` | 6 |
| `qcd` | 1 |

规则是**双向严格**：新增一条 → 红；基线里有而代码里没了 → 也红（提示棘轮往前走
一格）。后者是有意的：不逼着更新基线，这 547 条就会永远停在那儿，等于没有门禁。
每批翻译收尾时跑一次

```
QCODE_I18N_UPDATE_BASELINE=1 cargo test -p qcode-i18n
```

**踩到一个自己写的坑**：最初 `read_baseline` 用 `str::trim_end()` 去行尾空白，于是
字面量自带的尾随空格（比如 `"> 选择编号（…） "`）被吃掉，每次扫描都误报「新增 1
条 + 消失 1 条」。改成只剥 `\r`。这条记在这里，因为它说明「基线两边必须用**同一个**
编码/解码」这类错误是静默的。

词法器是手写的（约 120 行），不引 `syn`：仓库底线是「不为一次静态检查新增依赖」。
它处理行注释、**可嵌套**块注释、转义引号、`r#"…"#` 原始字符串，以及
`#[cfg(test)]` 之后整段不计入。有 3 条自测盯着它。

`scripts/check-i18n-golden.sh`：`en` 与 `zh-CN` 各抓 19 项（顶层 help ×2、15 个
子命令 help、2 种报错），当前 **39 项**。

- 每次都 `env -i` + 临时 `QCODE_DATA_DIR` / `QCODE_CONFIG`，**绝不碰真实数据目录**。
- `--version` 不入基线（内嵌 `git describe`，HEAD 一前进就变），改为断言「两种语言
  下逐字节相同」—— 那才是不变量。

#### 时长格式化：定了 `1m 23s`（已实现）

这个题目看起来是「一个词怎么译」，实际是**三个格式化函数、两套英文、一套中文并存**：

| 函数 | 输出 | 用在哪 |
|---|---|---|
| `format_duration_zh`（transcript） | `23秒` / `1分23秒` / `1小时2分3秒` | `工作中，用时 …`（每秒重算） |
| `format_duration`（transcript） | `23s` / `1m23s` | `耗时…`（工具耗时） |
| `format_duration`（TUI） | `500ms` / `1.5s` | TUI 状态行（亚秒级） |

前两个在**同一个视图里紧挨着**：思考行说「用时 1分23秒」，工具块说「耗时 1m23s」。
语言变成运行期维度之后，「哪套单位」不再能由调用点决定，所以合并成**一个**
`format_elapsed`，按 locale 分度。

**英文形态：`23s` / `1m 23s` / `1h 2m 3s`**（单位间有空格）。理由：

- cargo / GitHub Actions / Vercel 都是这个写法，读着不挤；
- 中文 `1分23秒` 与它**结构平行**（同样紧凑），两边宽度接近，实时计数器跨单位时
  跳动幅度一致；
- **不用 `1:23` 表盘式**：它有歧义（1 分 23 秒，还是 1 时 23 分？），而且与工具耗时
  的 `m/s` 形态并存时，又会重新变成「一个界面里两种写法」——只是把问题从跨语言
  挪到了同语言内部。

**不做零分量省略**（这一条是实测推翻了自己先前的设计）。原本打算「满一小时且分为 0
就省掉分钟」（`1h 3s`），写测试时发现它与实时计数器冲突：`59m 59s` → `1h 0s` →
`1h 0m 1s`，同一行文字先掉一个分量再涨回来。于是改成每个量级都写全，`1h 0m 0s`
照写。**秒数也始终显示**（含 `1m 0s`）：末尾跳动的数字就是「还在跑」的证据。

实现要点：

- 逻辑留在 Rust（`format_elapsed`），**只有字符串进 yml**（`app.duration.*`），
  翻译层不承担「选哪一条」的判断；
- 另出 `format_elapsed_in(locale, …)`，让测试能同时验两种语言而**不碰**进程级的
  `set_locale`（ADR-0105 §6）。为此在 `qcode-i18n` 加了 `trp_in`；
- 整句入 key（`app.elapsed.took` = `Took %{0}`），不把标签与数值分开翻——分开会拼出
  `Took1m 23s` 这种缺空格的怪句；
- 测试 4 条锁死形态：三种量级 + 两个边界（59/60 秒、59:59 / 1 小时）+ 负时长归零 +
  「跟随当前语言」。

TUI 那个亚秒级的**不动**：`500ms` / `1.5s` 里的 `ms`/`s` 是 SI 单位符号，本来就语言
中立，两种语言下都正确。

**踩到的坑（值得记住）**：新测试模块里写 `use super::*;` 直接让 `cargo test` 崩在
`SIGBUS` / `recursion limit reached while expanding #[test]`。这是本仓库**已记录过**
的坑（`render/mod.rs:315`、`window_icon.rs`）：`#[cfg(test)] mod` 里 glob 导入会把
crate 根一起带进来，多出的名字解析足以把 `#[test]` 的展开推过递归上限。解法是
**窄导入**。SIGBUS 是症状，给 rustc 更大栈（`RUST_MIN_STACK`）才看到真错因。

### 10.9 prompt 为什么改成英文，而不是留在中文

§2.3 原本写「prompt 永不翻」，处置是**保留中文**。本批改成了**写成英文**，理由是
「不翻」和「保持中文」不是同一件事：

- **「不翻」= 不随界面语言变。** 这一条没变，也不该变。
- **「保持中文」是历史状态，不是设计。** 这些指令是写给模型的，而模型读英文指令的
  训练配比远高于中文；更麻烦的是它们和同一个请求里的英文系统提示、英文工具名混排，
  同一段 prompt 里两种语言会让「照哪个格式答」变得含糊。`HAND_OFF_PROMPT` 本来
  就是这个症状：正文英文，只有 `已完成 (what is done)` 三个小标题是中文。
- **改成英文有明确成本，所以记在这里**：模型行为会变（尤其 `WRAP_UP_PROMPT` 的
  输出语言倾向）、eval 基线要重记、历史会话里已发出去的旧 prompt 不回改。

`frame_title_input` 与 `title_system_prompt` 的注释里都写着 *"the model owns the
language choice"*——**输出语言由模型按对话内容决定**，与指令本身用什么语言无关。
这正是「指令用英文、产出跟着用户语言」能成立的原因。

### 10.10 门禁 3 递归到整棵命令树（已完成）

P2 结束时留下的唯一「知道有洞但没补」：golden 只抓顶层与一级子命令，`sessions
delete` / `config init` 这类二级子命令的帮助不在基线里（`§10.8` 的 P2 记录第九点）。

**洞的根因不是「少抓 6 项」，是那张手写列表。** 脚本里原本有一个

```bash
SUBCOMMANDS=(tui run resume sessions schedule daemon skills logs config template
             mcp doctor shell-env update acp)
```

加一个子命令不会有人记得回来加一行，于是 golden 悄悄不覆盖它——这就是我那两条
`long_about` 被截断却全绿的原因。所以补法不是把列表加长，是**让它消失**：用例集合
改成从二进制自己的 `--help` 递归发现。

- 读 `Commands:` 节里「两个空格 + 小写名字」的行，`help`（clap 自动加的）跳过；
- 逐层递归，深度上限 4（现在最深是 `config key set`，三层）；
- 39 项 → **87 项**（43 用例 × 2 语言 + `--version`）。

**写这一版时踩的坑，值得单独记：发现必须固定用 `en` 跑。** 第一版把「当前正在抓的
语言」传进了发现函数，于是 `zh-CN` 那轮一个子命令都没发现到——中文的锚点是「命令：」
而不是 `Commands:`。结果 48 项里 zh 只占 4 项，而门禁**照样报「通过」**。这类 bug 的
形状是「覆盖率腰斩但全绿」，比直接报错危险得多；发现后改用 `en` 做锚点，理由也顺：
英文帮助本身由不变量 1 钉着逐字节不变，拿它当解析锚点比拿中文稳。

**反向验证过会红**：把 `config init` 的 `long_about` 第二段从 yml 里删掉（复刻 P2 那个
bug），新门禁立刻在 `help-config-init` 上报差异，差异内容正是丢掉的那段。

**顺带补的两个跨平台窟窿**（都是 P2 引入、被这次递归暴露的）：

1. **门禁 7 只对「用户看得见」的项要求译文。** Windows 下命令树多出四个
   `#[cfg(windows)]` 子命令，其中三个是 hidden 的内部命令（`sandbox-probe` /
   `sandbox-run` / `whoami`）。它们不出现在 `--help` 里，中文界面也就不会露出英文，
   所以留英文是**有意的**，门禁按 `is_hide_set()` 跳过（隐藏的**参数**同理，如
   `--child`）。可见的那个 `sandbox` 补了 5 条译文。
2. **「声明了却查不到」对别的平台的命令要豁免。** 在 macOS / Linux 上 `sandbox` 根本不
   进命令树，所以那几条 key 必然「查不到」——`OTHER_PLATFORM_ONLY` 显式列出这个前缀，
   而不是靠 `cfg` 分支（两头都成立：Windows 上查得到，豁免不起作用）。

**已知限制（未变）**：基线是单一平台形状。`sandbox` 只在 Windows 存在，所以 Windows 上
跑这条门禁会因为顶层多一行而失败。门禁 3 只在 `make check` 与 release 里跑（不进 CI
矩阵，CI 是 macOS / Ubuntu），目前不算问题；真要跨平台跑，得先决定平台相关命令怎么进
基线。脚本头部与 `§8.1` 都记着这一点。

### 10.11 补洞：门禁 2 的英文面、颜色门禁、宿主语言假绿（已完成）

§10.10 收尾时记了一句「已知限制」。之后把「还有哪些洞」逐条实证了一遍，四个真问题：

**一、门禁 2 只查汉字，英文硬编码完全没有门禁。** 判定是
`literal.chars().any(is_han)`，于是「中文界面里露出英文」这一类它一个字都说不出。
实际漏了 **170 条**（`forms.rs` 150 条字段 label/help + `Page::title()` 11 条页面名 +
`render.rs` 6 条按钮/分组 + 1 条 aria label），全在设置页/向导——P1 里最大的用户面。

**怎么补的，以及为什么不按内容判。** 新增 `no_new_hardcoded_english_ui_text`，按
**位置**判：只认紧跟在 `.label(` / `.aria_label(` / `group_heading(` / `label: ` /
`help: ` / `title: ` 之后的字符串字面量（`forms.rs` 另加 `=> `，那是 `Page::title`
的 match 臂）。

一开始想按内容判（首字母大写、含空格…），放弃了：`"Sandbox"` 是界面标题，
`"ModelMenu"` 是 widget id，`"running"`/`"queue"` 是状态名——都是单个英文单词，
凭内容猜只会两头误判。而「位置」在这份代码里是确定的：这些位置只可能装文案。
**改成 `tr()` 之后检测器自动不再算它**（`literal_after` 只认紧跟 `"` 的），
所以修一条、基线就短一格，不需要另外维护。

**二、不变量 1 的后半句（en 保留颜色）没有任何门禁。** golden 主流程固定
`NO_COLOR=1`，因为带转义码的 diff 不可读。代价是：把 en 路径从原生
`Error::exit()` 改成 `render().to_string()`——**文本逐字节相同、只是丢了颜色**——
87 项照样全绿。我实测过这个绕过。

这不是假想：中文路径**本来就无色**（`StyledStr::Display` 明确 colorless），所以颜色是
整个双语化里**只有 en 享受到**的东西，也最容易被「顺手统一渲染路径」改掉。补法是
脚本里加一条：用 `script` 造伪 TTY（macOS 与 Linux 参数不同，两头都试），断言 en 的
stderr 带 `\033[`。反向验证：故意丢色 → 直接红。

**三、`Heading` 规则是个「靠调用方 if 撑着」的隐雷。** 它无条件
`trim_start_matches(' ')`，所以英文 `Usage: qc` 会变成 `Usage:qc`。当时无害，只因为
`main.rs` 里有个 `if locale == DEFAULT { error.exit() }` 让 en 根本不进规则表——也就是
说**正确性依赖一个可以被删掉的守卫**。

改成从**译文本身**判断（`join_after_heading`）：译文以全角冒号结尾就吃掉空格，否则
保留。这样两种语言都是**构造上正确**，不再依赖调用处纪律。验证方式是把那个 `if` 换成
`if false` 让 en 硬走规则表：文本仍逐字节一致（只剩颜色差异，由上面第二条门禁抓）。

**四、两条测试一直是红的 / 靠宿主语言才绿。** 这类洞没有任何门禁能抓，只能靠跑全量。

- `crates/qcode-gui/tests/tray_state.rs` 三个测试断言中文托盘文案，但集成测试**不会**
  自动调 `init()`，全局 locale 停在 rust-i18n 的默认 `en` → 一直红。它没被发现是因为
  `cargo test -p qcode-gui --lib` 跑不到 `tests/`。
- `crates/qcode/tests/schedule_cli.rs` 与 `schedule_registration.rs` 断言中文 CLI
  输出却没设 `QCODE_LANG`，**只在本机（中文 macOS）通过**——换台英文机器就红。
  这是个「假绿」：测试的通过与否取决于跑它的人的桌面语言。

两条都按 ADR-0105 §6 钉死（前者 `pin_for_tests()`，后者 `QCODE_LANG=zh-CN`），并且在
`LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8` 下复跑确认。

**顺带纠正一处文档自述**：§8 一直说「11 条全部是有意不翻（原生对话框 7、厂商商标 4）」。
实际那 11 条里混着 **3 条真漏翻**，方向还更糟——是**英文用户看到中文**：
`setup/render.rs` 的 bwrap 缺失提示、`runtime.rs` 的两条驱动锁提示。已改成走 `tr()`，
中文基线 11 → **8**（2 条 PowerShell 中文 + 4 条厂商商标 + 2 条原生对话框标题，最后
这两条在 `platform.rs` 里本来就有 `native_ui_is_zh()` 的英文分支配对）。

**棘轮现状**：英文基线 170 → **152**（修掉 18 条：6 处散落 + 11 个页面名 + 1 条 aria
label），剩下的 151 条在 `forms.rs`（设置页字段表），加 1 条 `linux.rs` 的 `"QCode"`
应用名（品牌，有意不翻）。`forms.rs` 那批是**独立的翻译批次**，不该混进补洞的改动里
——它要 150 条中文，且需要把 `FieldSpec.label` 从「英文原文」改成「译文 key」再接线，
是一次结构性改动。**这是目前唯一已知的残留视觉缺陷**：中文用户的设置页字段名与
说明仍是英文。

**验证**：`cargo fmt --check`、`clippy -D warnings`、全 workspace **1434 项**测试（含
集成）全绿、当时那七道门禁 + golden 88 项全绿；两个新门禁都做过反向验证。

### 10.12 设置页数据表：把英文原文换成译文 key（已完成）

`forms.rs` 的 `FIELDS` / `GUI_FIELDS` / `TABLES` 是三张 `const` 数据表，`label` /
`help` / `title` 里放的是**英文原文**——154 条。这是 P1 之后仅剩的成片英文界面：
中文用户打开设置页，字段名和说明全是英文。

**为什么当时没翻。** 它和前面所有批次的形状都不同：不是「写死的文案」，而是「数据表
里的一个字段」。逐条套 `tr("…")` 无处可套——渲染点只有一个，数据是遍历出来的。所以
必须先把字段的**语义**从「英文原文」改成「译文 key」，再在唯一渲染点翻译。这是个结构
改动，不该混进补洞的 commit。

**做法。** 三张表的对应字段现在装 key，命名跟数据路径走：

| 来源 | key |
|---|---|
| `FieldSpec.label` | `gui.setup.spec.<path>.label` |
| `FieldSpec.help` | `gui.setup.spec.<path>.help` |
| `TableSpec.title` | `gui.setup.spec.<path>.title` |
| `ColumnSpec.label` | `gui.setup.spec.<path>.col.<列key>` |

翻译只发生在五个渲染点（`aria_label` ×3、`help_popover`、表标题/列名）。`help`
一路是 `&'static str`，现在到渲染前才变成 `Cow`：`HelpInlineData` 与 `help_popover`
都改成收 `Cow<'static, str>`——数据表是 `const`，译不了语言，所以翻译必须发生在
渲染期。

**英文侧零改动**：yml 里 154 条的 `en` 就是原来的英文原文逐字抄下来的，所以
`en` 渲染结果与改动前完全一致（golden 88 项零差异）。

**门禁 8，以及写它时踩的坑。** 与 `cli.cmd.*` 同理：`gui.setup.spec.*` 是运行期拼的
key，门禁 6 看不见，所以放行该前缀并新增 `spec_i18n.rs` 双向比对。

第一版的门禁是**错的**，而且错得很隐蔽：它用 `field.path` **重新推导**一遍 key
（`format!("gui.setup.spec.{path}.label")`），而不是读字段里真正存的那个字符串。
于是它只验证了「yml 里每个 path 都有条目」——代码里 key 拼错（把 `max_turns` 写成
`maxTurn`），它**照样全绿**。

这个 bug 是被**反向验证**抓出来的：按惯例故意把一条 key 改错，发现门禁没红。改成直接
读 `field.label` / `field.help` / `table.title` / `column.label` 之后，三个方向都验过
会红：代码 key 拼错、yml 漏译文、yml 有孤儿 key。另外补了「同表列 key 重复」一条——
重复时 `ColumnSpec` 查找会静默取到同一个格子，两行显示同一个名字。

**一个容易漏的细节**：字段表有**两张**（`FIELDS` 与 `GUI_FIELDS`，后者是外观页的 5 个
字段）。第一版只走了 `FIELDS`，于是外观页那 10 条译文被门禁判成「声明了却没人用」。

**棘轮现状：英文基线 152 → 1。** 只剩 `linux.rs` 里的 `"QCode"` 应用名（品牌，不翻）。
中文基线仍是 8（全部有意不翻，见上一节）。

> 这个「1」是**当时**的数。§10.15 把门禁的位置表扩到 CLI 命令输出后，一批原本在缝里
> 的文案（161 条）一次性进了基线，现为 56 条待还——不是退步，是那些债之前没被记账。

**未验证的部分**：设置页界面本身没有截图/golden 覆盖（GUI 需要真窗口）。这批的正确性
靠三件事支撑：`en` 侧原文逐字未变、154 条 key 在两种语言下都取得到（门禁 8）、
翻译发生在唯一渲染点。真要视觉复核，得人工开窗口看一遍中文设置页——这是本批唯一
没有机器证据的地方，记在这里。

### 10.13 P3：工具输出跟随 UI 语言，以及一个被数字掩盖的空缺（已完成）

**先说结论：P3 原本以为在 P1 就做完了，实际没有。**

§7 的表格把 P3 记成「工具输出 58 条」。P1 结束时 `qcode-tools` 的中文基线确实清零，
于是看起来做完了。但清零的是**中文**：P1 把那 58 条中文改写成英文，`ToolOutput::ok`
里的返回值也一并写成了英文——**却从来没有接 `tr()`**。所以中文用户在一次带工具调用
的对话里，看到的工具结果始终是英文（`no matches`、`wrote 64 bytes to …`）。

这不是笔误，是记账方式的问题：「中文清零」被当成了「i18n 完成」，而 §2.3 真正要求
的是「结果面跟随语言」。两者在英文原文上恰好重合，只有回头看代码才分得开。

**一、58 条其实是三件事。** 实测拆开（2026-11-22）：

| 类别 | 数量 | 处置 |
|---|---|---|
| 工具 spec 顶层 `description` + 参数说明 | 56 | 保持英文 |
| `ToolError` 技术诊断 | ~14 | 保持英文 |
| `ToolOutput` 结果摘要 | 8 个 key | 翻 |

边界重新划定的理由写在 ADR-0105 §5 的修订里；这一节记实施。

**二、P1 留下了一处真实的混排，这批回退掉了。** P1 把 `schedule_*` 四个工具的
**11 条参数描述**翻成了中文（`"description": tr("tool.schedule.param.title")`），
而其它工具的 spec 全是英文。中文用户的一次请求里，`schedule_create` 的参数说明是
中文、`read_file` 的是英文——正是 §2.3 自己警告的「同一段 prompt 两种语言会让『照
哪个格式答』变含糊」。

这 11 条回退成英文，英文原文从 `locales/app.yml` 逐字抄回代码，词句未变；对应的
`tool.schedule.param.*` 11 个 key 删除。全仓工具 spec 重新统一为英文。

**三、接线的 8 个 key，其中 3 处埋在 `qcode-core` 里。** 结果摘要散在多个 crate：

| key | 位置 |
|---|---|
| `tool.fs.image_returned` / `wrote` / `replaced` | `qcode-tools/src/fs.rs` |
| `tool.search.no_matches` | `qcode-tools/src/search.rs` |
| `tool.shell.timed_out` | `qcode-tools/src/shell.rs` |
| `tool.fetch.cancelled` / `tool.web_search.cancelled` | 各自的工具 |
| `tool.cancelled` | `shell.rs`、`ask.rs`、**`qcode-core/src/engine/tools.rs` 三处** |

最后一行是清单外的：引擎在「一轮被中断」时给每个未执行的工具补一个
`ToolOutput::cancelled("cancelled by user")`（为了保持 one-call-one-result 不变量），
那三处同样是用户看得见的结果面。与 `shell` 的取消是同一个概念，所以共用一个 key，
而不是各写一份。

**四、门禁扩了，但 `push_str(` 必须排除。** 位置表加了 `ToolOutput::ok(` / `err(` /
`cancelled(`，扫面从 4 个 crate 扩到全部 16 个（中文门禁本来就扫全部，英文面只扫一半
是不对称的）。

第一版还加了 `push_str(`，结果一次冒出 31 条，其中 9 条是 `qcode-tools/macos.rs` 里
拼 `sandbox-exec` profile 的 DSL（`(allow file-read*`）、1 条是纯换行 `"\n\n"`。
**把 sandbox DSL 翻成中文，沙箱规则就失效了。** 位置判据在通用字符串 API 上失效，
所以收窄成只认 `ToolOutput::*` 这一个构造入口。

收窄后剩 4 条真命中，全是工具取消输出（`ask.rs` / `fetch.rs` / `web_search.rs` /
`shell.rs` 各一条），正好是这批该接的。接完基线零新增——意味着 `qcode-tools` 从此
是**零容忍**，新增硬编码工具输出立刻红。反向验证：把 `no matches` 改回字面量，门禁红。

**五、三条测试因此变脆，改成钉 `zh-CN` 断言中文——顺带又照出第四条。**
`search.rs` / `tools.rs` 里断言 `"no matches"`、`"cancelled by user"`、
`"timed out after 1s"` 的测试，在接线后依赖进程 locale，而集成测试默认停在 `en`
（`pin_for_tests()` 只在显式调用的地方生效）。

中间试过用 `tr(key)` 反查期望值，**这是错的**：`en` 下 `tr(key)` 恰好等于原来硬编码
的英文，于是「压根没接线」和「接线正确」在测试里看不出区别——反向验证时一测就露。
改成 `pin_for_tests()` + 断言中文原文，硬编码英文会立刻红。

钉住之后，`read_file_returns_a_picture_as_an_image` 跟着红了（它断言 `contains("bytes")`）
——因为 `pin_for_tests` 是进程级的，同二进制里所有测试一起转中文。第四条断言就是这么
被照出来的，改成 `contains("字节")`。

**六、不翻的那些，是有意的。** `ToolError` 的 ~14 条技术诊断不翻：受众是模型，它要
据此改参数重试，`glob` / `regex` / `hunk` / `UTF-8` 翻成中文反而更难对上错误信息。
`exit code: N` / `signal` 同理，是 shell 约定的技术标记。这些都记在 yml 的注释里，
免得下一个人以为是漏的。

**七、数字。** 中文基线 **8 → 8**（没有新增中文，这批判的是「英文改走 tr」）；英文
基线 **1 → 1**（同样不变，`qcode-tools` 存量直接清零，未进基线）。`tool.*` 段现有
**37 个 key**：8 条结果摘要（本批新增）+ `tool.schedule.*` 29 条（P1 已接线，含
unavailable / ask / error / output）。

**没有机器证据的地方**：工具结果在 GUI 里长什么样没有截图基线（同 §10.12）。正确性
靠三件事：端到端实测同一调用在 `zh-CN` 下得「没有匹配」、`en` 下得 `no matches`；
门禁 2 英文面零容忍；4 条断言钉语言后钉住中文原文。

### 10.14 `[ui] language`：让「双击启动的 GUI」也有语言可选（已完成）

P0 起语言来源就是 `QCODE_LANG` → 系统首选 → `en`。这条对一个从终端敲 `qc` 的人够用，
对**双击图标启动的 GUI** 不够用：那里没有 `QCODE_LANG`，能选的只有「系统语言」。这次
把它补完，顺便把 §9 剩下的三条未决一起结掉。

**一、配置项是一个自由字符串，不是枚举。** `[ui] language`，与 `busy_delivery` 同段：

```toml
[ui]
language = "zh-CN"   # 或 "en" / "auto" / 任何 locale 标签
```

不用枚举的原因：locale 标签的组合太多（`zh-Hans-CN`、`en_GB.UTF-8`、`fr`），枚举会把
它们全变成**反序列化错误**，而正确行为是「认不出就跟随系统」。校验交给
`qcode_i18n::normalize`，它本来就负责 `zh-Hans-CN` → `zh-CN`、`C.UTF-8` → `en` 这些。

`auto` 因此**不需要特判**：`normalize("auto")` 认不出 → `None` → 落回系统判定。这条
性质有测试盯着（`explicit_treats_auto_as_unset`）——如果哪天有人给 `normalize` 加一条
`"auto" => Some(EN)`，中文用户选了 auto 就会看到英文。

`CONFIG_VERSION` 没有 bump：`serde(default)` 让老文件照读。

**二、`qc` 有两次机会，GUI 有一次，daemon 是例外。**

| 进程 | 什么时候定语言 | 优先级 |
|---|---|---|
| `qc`（第一次） | clap 之前 | `QCODE_LANG` > 系统 > `en` |
| `qc`（第二次） | 配置读出来之后 | `QCODE_LANG` > `[ui] language` > 系统 |
| GUI 三个入口 | 窗口建起来之前（配置路径已在手上） | `QCODE_LANG` > `[ui] language` > 系统 |
| `qcd` | 装配之后、驱动循环之前 | **`[ui] language` > `QCODE_LANG`** > 系统 |

`qc` 为什么要两次：帮助与解析报错是**解析时**求值的，那时配置还没读。所以
`qc --help` 仍按环境变量/系统定语言，而**命令的输出**跟随配置。这个不对称是真的，记在
这里而不是假装没有：`--help` 用英文、`qc schedule list` 用中文，同一次配置下会同时
出现。

要消掉它就得在 clap 之前扫一遍 argv 找 `--config`。没做——那会把「配置解析」变成两处，
而且 `qc run "--config"` 这种位置参数会误伤。收益（`--help` 也跟着配置）不值这个风险，
何况真要 `--help` 变语言，`QCODE_LANG` 一直有效。

**三、daemon 反过来，这是本批唯一一处「违反自己定的优先级」的地方。**

`qcd` 没有界面，它的环境变量来自**启动它的那个 shell** —— 可能是一个写死了
`QCODE_LANG` 的 CI 容器、一个 dotfile、或者 GUI 转手 spawn 时继承的空环境。让那种东西
决定「用户明天早上看到的定时提醒是什么语言」是不对的。配置文件是用户为**这台机器**做
的选择，正是应该影响任务产出的东西。

所以 `init_for_daemon` 让配置压过环境变量。做法上没有靠注释约定，而是把判断抽成纯函数
`daemon_decision(configured, env, system)` 并配矩阵测试，其中两行是**对照组**：同样的
输入走 `decide` 得到相反结果。以后谁想「顺手统一」这两个函数，测试会当场变红。

配置没说（`None` / `auto`）时仍然尊重 `QCODE_LANG` 与系统——没有矛盾需要裁决。

配置重载**不**动语言：ADR-0105 §9 定的是「改配置后重启生效」，日志里那条
`reloaded configuration` 不该顺手换语言。

**四、设置页那个下拉，以及顺带修掉的一个显示 bug。**

`ui.language` 进 `Page::Agent`（和 `busy_delivery` 挨着），**不进** `Page::Appearance`：
后者按设计只收 `gui.json` 的字段（SETTINGS-UI-V2.md §4.2 有这个拆分理由），把一条
config.toml 字段塞进去会让那一页出现两种保存位置。

写这个字段时发现 `scalar_string`（表单的读方向）末尾是一条
`_ => options.first()`：**任何忘了写分支的下拉框都会永远显示第一个选项**。
`[ui] busy_delivery` 就踩了这个——配置写 `steer`，界面显示 `queue`，写回又是对的。
用户看到的是「我改了没生效」，于是再点一次。现在两条都补了分支，并各有一条测试
（反向验证：把它改回常量，测试红）。

**五、`apply_config` 是逐字段枚举的，漏一行就静默丢值。**

设置页保存走 `ConfigEdit::apply_config`，它把每个字段显式写一遍。新增字段只加在结构体上
是不够的：**值在内存里改了，落盘时没人写它**，表现是「设置页能选、保存后消失」。
`apply_config_round_trips_all_sections` 里补了这个字段的断言，反向验证过——删掉
`apply_config` 里那一行，断言立刻变成 `None`。

**六、`schedule_edit` 的四个参数描述。** 同一批补的，属 §10.13 划定的「spec 保持英文」
那一类：`title` / `prompt` / `target` / `overlap` 原来**没有 description**，模型只能
借用 `schedule_create` 的说法，而 create 里那四条都写着「可省略，工具会反问」——语义
正好相反（edit 是「改哪个字段，不改就保持」）。四条都按 edit 的语义重写，并统一带上
「omit to keep the current one」；`approval_timeout_secs` 顺手补上「pass null to
clear it」——那是它唯一有意义的非常规取值，原来只在 create 的说明里能猜到。

**七、验证。**

- 单测：`explicit` 的 `auto` 归一化表、`daemon_decision` 优先级矩阵（含与 `decide` 的
  对照）、`[ui] language` 反序列化与「是已知键」、设置页两条下拉的读写、`apply_config`
  round-trip。
- 端到端：`qc --config <只写 language="zh-CN" 的文件> schedule list` → 中文；
  同一文件写 `en` → 英文；`QCODE_LANG=zh-CN` + 配置 `en` → 中文（环境变量赢）。
- 冒烟：`qcd` 带 `[ui] language` 起得来，日志里**没有**unknown-key 警告（已知键表补过了，
  否则示例配置会自己骂自己）。

**没有机器证据的地方（第二处）**：daemon 的语言只验到「读对了配置」这一层——真正
「定时任务触发的那个回合里，工具结果是不是中文」需要搭一套定时任务 + 会话才能观察，
这次没做。判断依据是 `daemon_decision` 的单测 + 调用点在装配之后、驱动循环之前这一条
代码事实。记在这里，免得以后把它当成已经验过的东西。

### 10.15 CLI 命令的输出：把「两条门禁都看不见」的那 161 条收进账

用户报的现象是：「配置成中文，`schedule list` 是中文而 `sessions list` 是英文。」
查下来 `crates/qcode/src` 有 **161 条**用户可见的输出文案是硬编码英文，而**中文门禁与
英文门禁都看不见它们**：

- 中文门禁只找汉字；
- 英文门禁的位置表里没有 `println!` / `eprintln!` / `write!` / `push_str`——P3 时为
  了不误伤 `qcode-tools/macos.rs` 的 sandbox-exec profile DSL（`(allow file-read*`）
  而刻意排除了它们。

于是这一整面就是两个门禁之间的缝。

**一、先接线的是完整的三块（daemon / logs / sessions，共 33 条）。**

| 位置 | 内容 |
|---|---|
| `commands/daemon.rs` | `start` / `stop` 的 13 条（`already running`、`cannot start`、`stopped`、`wedged`…） |
| `commands/logs.rs` | 5 条（`no log files in`、`waiting for the first line`、`searching N files`…） |
| `commands/sessions.rs` | 10 条（`no sessions`、`nothing to clean`、`dry run; pass --yes`、三平台的钥匙串提示…） |

钥匙串那三条有个细节值得记：`stored in the keychain; add to your config:` 后面跟的是
`api_key_command = [...]` 配置片段。**只翻前一句**，片段逐字保留——那行是要用户粘进
`config.toml` 的，翻了就废了。

**二、门禁扩了，但只加 `println!` / `eprintln!`，不加 `push_str` / `write!`。**

理由是实测出来的：加前两个一次冒出 63 条真债且零误伤（sandbox DSL 不打印）；加后两个会
把 `macos.rs` 的 9 条 profile DSL 和 `apply.rs` 的纯换行 `"

"` 一起算作文案。

另外加了一条**格式规则**：行首是 `[tag]`（内部无空格）的行不算文案。它一次豁免了
`[tool]` / `[approval]` / `[ask]` / `[warn]` / `[turn]` / `[budget]` 这类进度标记——
那些方括号段是给人 `grep '^\[tool\]'` 用的（本次排查我自己就在用），翻了就没了。
这不是「像不像文案」的猜测，是一条可判定的形式判据。

`qcode/src/output.rs` 整文件豁免，因为它全是两种情况之一：
`qc config show` 的 `键 = 值` dump（要能 grep/diff，且没有 `--json` 旁路），
以及 `[tool] ok (123 bytes)` 这种进度标记。

**三、基线从 1 条涨到 56 条——这是**变得**更诚实，不是变差。**

扩门禁那一刻，161 条里没接线的一次性全暴露出来，进了
`scripts/i18n-baseline-en.txt`。棘轮从此看住它们：**只允许减少**。

这 56 条是「还欠着的债」的清单，按文件：`settings.rs` 13、`misc.rs` 13、`update.rs` 8、
`run.rs` 4、`doctor.rs` 3、`sandbox_probe.rs` 2，其余是 `qcd` 的两条（`qcd --help`
有意英文，见 §9 第 1 条）、`logging.rs` 的一条日志（有意英文）、`approval.rs` 的六条
`[approval]` 明细行、以及 `QCode` 品牌名。

**这一批没有把 56 条做完，如实记在这里。** 中途试过 `doctor.rs`，做到一半发现它
有 72 个 `ok/warn/fail` 调用点、22 个标签加约 45 条细节，而且标签是动态拼的
（`mcp probe {server}`）——只翻标签会得到「标签中文、细节英文」的混排，违反
ADR-0105 §9 不变量 5（一个提交内不得一半翻一半没翻）。于是整文件回退，留到专门的一批。

**四、两处测试因此变脆，都按 §6 钉住了。**

`daemon_cli.rs` 的 3 条和 `sessions_delete.rs` 的 1 条原来断言英文输出——它们以前
「碰巧两头都过」，因为输出是硬编码英文、与宿主语言无关。接线之后它们依赖进程语言，
于是：钉 `QCODE_LANG=zh-CN`，断言改中文原文。这正是 §10.11 记过的同一个模式（宿主
语言假绿），这次是第二次撞见，所以把「新增断言 CLI 输出的测试必须显式钉语言」写成了
`qc()` 辅助函数里的默认值，而不是每条测试各记一次。

**五、验证。**

- 端到端两语言：`sessions list` → `no sessions` / 没有会话；`daemon stop` →
  `qc daemon: not running.` / `qc daemon：没有在跑。`；`logs` → 路径不翻（数据）。
- 门禁反向验证：在 `misc.rs` 里加一句 `println!("Doctor will run all checks")`，门禁红。
- `fmt`、`clippy -D warnings`、八道门禁 + golden 88 项、qcode 175 / gui+tools 357 /
  i18n 18 全绿。

### 10.16 把 56 条还到 3 条：棘轮要能归零，就得把「债」和「决定」分开

§10.15 把基线从 1 记到了 56。这一批把它还到 **3**，过程中修了三条门禁自身的 bug。

**一、先分开「待还的债」和「有意不翻的决定」。**

56 条里混着两类东西，混在一张表里，棘轮永远降不到零，也就看不出还剩多少：

| | 是什么 | 归宿 |
|---|---|---|
| 债 | 该翻没翻 | 基线，只许减少，**目标为零** |
| 决定 | 翻了会坏，或本来就不面向人 | `intentional_english()` 豁免表，带理由，不随时间减少 |

豁免表现在 5 条（都写了理由）：`qcd/main.rs`（`--help`/`--version` 必须在任何初始化
之前就能回答，§9 第 1 条已定）、`qcode-kernel/logging.rs`（日志，ADR-0105 §4）、
`qcode-gui/linux.rs`（`QCode` 品牌）、`qcode-tools/windows_acl.rs`（沙箱 helper 子进程
的 stderr 前缀）、`qcode/src/sandbox_probe.rs`（沙箱诊断工具，读它的人在对 ADR 与
`sandbox-exec` 文档排障）、`qcode-core/approval.rs`（`[approval]` 的结构化明细，
与 `qc config show` 同类：字段名要能 grep）。

**二、三条门禁 bug。都不报错，只是**看不见**——这种最值得修。**

1. **多行调用漏扫。** `println!(
    "shell: {} …"` 的字面量在下一行，而
   `literal_after` 只看当前行。`qc shell-env` / `qc doctor` 都是这么写的——于是
   整个 doctor 的明细从来没被扫到过。修完一次冒出 27 条。
2. **续行被当成转义。** `"…… \
   …"` 里的 `\`+换行是 Rust 的续行（换行与缩进一起
   被吃掉），按转义处理后一条文案被切成几段，基线里出现只有缩进和 `\x20` 的碎片行。
3. **重复计数。** 修多行时我把「本行 + 后两行」拼成窗口，于是同一句在含标记的行和
   上一行的窗口里各被数一次。`ui_text_detector_skips_key_shaped_strings` 抓到了它
   （期望 1、实得 2）——那条测试原本是给「key 形态不算文案」写的，结果先抓到了这个。

**三、两条新的格式判据（都是可判定的形式规则，不是「像不像文案」的猜测）。**

- **纯占位符不算文案**：`{report}`、`{HELP}`、`{}`、`"{}\n{}"` 里一个「字」都没有，
  全是插值。`println!("{report}")` 这种写法很常见，文案留在 `report` 里。
- **`--- ` / `+++ ` 开头是 diff 文件头**：`qc config init` 与 `qc config append` 都先
  打一段 diff 让人确认，那两个前缀是补丁语法，翻了两边对不上、`patch` 也不认。

**四、按文件还的过程里，有一处旧决定被推翻。**

`cli.update.*` 原先写着「英文主干保留在代码里（`warning: …`），这里只放尾巴那句解释」。
照这个口径，中文界面上会出现 `warning: 无法下载 qcd：…`——半英文半中文，正是
ADR-0105 §9 不变量 5 禁止的形状。改成整行一个键，`warning:` 也翻成 `警告：`，
5 条旧的「尾巴键」合并进对应的整行键。**同一个不变量，上批用它否决了 doctor 的半截
翻译，这批用它否决了 update 的半截翻译。**

**五、`output.rs` 的整文件豁免有个漏洞，补上了。**

`pause_line()` 住在 `output.rs`（豁免文件），但它返回的是**给用户读的散文**
（`used 3/5 turns`）而非配置 dump。文件级豁免会连它一起放过去。已改为走 `trp()`。
`output.rs` 真正豁免的是 `qc config show` 的 `键 = 值` 与 `[tool]` 这类进度标记。

**六、测试又脆了 4 处，都按 §6 钉住。**

`budget_pause.rs`（暂停行）、`skills_list.rs`（计数行与「技能已关闭」）、
`update.rs`（`有可用更新` / `已是最新版本`），加 `daemon_cli.rs` /
`sessions_delete.rs`（上批）。**这是第三次撞见同一个模式**：新增断言 CLI 输出的测试
必须显式钉 `QCODE_LANG`，否则「碰巧在作者机器上过」。已在每处留注释指向 ADR-0105 §6。

**七、现状与剩余。**

| 文件 | 本批前 | 本批后 |
|---|---|---|
| `settings.rs` | 21 | 0 |
| `update.rs` | 16 | 0 |
| `misc.rs` | 9 | 0 |
| `run.rs` | 4 | 0 |
| `sessions.rs` | 3 | 0 |
| `sandbox_probe.rs` | 1 | 0（转为豁免决定） |

`doctor.rs` 单独一批：它不只 3 条。那 3 条只是**格式串开头**（`all checks passed` 等）；

### 10.17 `qc doctor`：门禁看不见的那一半，以及为什么它躲过了两轮扫描

§10.16 收尾时基线只剩 3 条，但那 3 条只是**格式串开头**。doctor 真正的量不在这里：
22 个标签 + 约 60 条明细，全部藏在 `self.ok(label, detail)` 的**第二个参数**里，
而位置表里的 `println!` / `eprintln!` 只认「标记之后的第一个字面量」。

**一、门禁为什么两轮都没看见它。**

`literal_after` 拿的是「标记之后（跳过空白）的第一个 `"…"`」。对
`self.ok(key, "detail")` 这种调用，第一个字面量是**位置参数里的标签**（改之前是
`"data dir"` 这样的散文，改之后是 `cli.doctor.label.data_dir` 这样的 key）——
无论哪种，明细都在它后面，永远轮不到。

于是 doctor 同时满足两个条件：中文门禁只找汉字（英文不会触发），英文门禁取不到
第二个参数。它落在两条门禁之间的缝里，而且**缝得很整齐**：一个文件、一整个子系统。

**二、修法：让位置表能取「标记之后的全部字面量」。**

新增 `is_multi_literal_marker`（`self.ok(` / `self.warn(` / `self.fail(` /
`doctor.*`）与 `literals_after`，对这几个标记取全部字面量：标签因为形状像 key 被
`is_key` 滤掉，明细照查。

**这里有一次真实的失败值得记**：第一版 `literals_after` 是循环调用 `literal_after`，
写完门禁照样绿——我差点以为「扩了」。反向验证（把一条明细换回英文）才暴露它一条都
没取到：`literal_after` 要求「标记之后立刻是引号」，而实际调用里引号前面还有
`qcode_i18n::tr(` 之类。**没有反向验证，这个 bug 会以「门禁已覆盖」的假象长期留着。**

**三、接线时踩到的两件事。**

1. **数组里的间接引用对门禁是「没人用」。** 我有两处把 key 塞进数组再在循环里
   `tr(field)`，门禁立刻以「声明了但没人引用」报错。它不是死板：能 grep 到的引用
   才是引用。改成在数组里直接 `tr("…")`。
2. **跨 crate 的自述文案。** `sandbox.describe()` / `grant.describe()` 在
   `qcode-tools` 里，而 `qc doctor` 只负责打印。它们**也给授权报错用**
   （`qcode-kernel` 的 `(grant: …)`），所以翻译只能落在定义处，不能落在 `qc` 的
   打印处。`qcode-tools` 本来就依赖 `qcode-i18n`，新增键在 `core.sandbox.describe.*`。
   机制名（`sandbox-exec` / `bubblewrap` / `Landlock` / `windows-acl`）不翻：用户要
   拿它对照 man page 与 ADR。

**四、测试：一整个文件钉 `en`，另加一条真正验中文的。**

`doctor_mcp.rs` 的 23 条测试断言的是**原因文案本身**（`does not exist; the grant
skips it` 之类）。把 89 条断言改写成中文，diff 会盖住真正的改动，也容易把断言改弱。
所以：钉 `QCODE_LANG=en` 让那 23 条继续检英文文案的正确性，另加
`doctor_speaks_chinese_when_asked` 专盯中文——标签、明细、汇总三处都必须是中文，
并显式断言英文原文**不再出现**（`!text.contains("data dir:")`）。

这条测试盯的正是 ADR-0105 §9 不变量 5：不允许「标签中文、明细英文」的半截状态。

**五、仍有意保持英文的两处（都在豁免表里，不是漏）。**

- `[ok]` / `[warn]` / `[fail]` 行首标记：`grep '^\[fail\]'` 是真实用法（I18N.md
  §10.15 已记）。
- 各平台的 `qcode-resolved` 路径、版本号、来自下层 crate 的错误串：运行期事实，
  不是这句话的一部分。判据是「路径不翻是数据」（§6 第 6 条）。

**六、现状：英文基线归零。**

| | 条数 |
|---|---|
| 基线（待还的债） | **0** |
| 豁免表（有意不翻的决定） | 6 个文件 |

从 §10.15 的 1 → 56（扩门禁，把债记账），到 §10.16 的 56 → 3（按文件还、分账），
到这里的 3 → 0。**这一面做完了**，且从此有门禁守着：任何新写的
`self.ok/warn/fail(_, "English text")` 都会红。

**七、验证。**

两语言冒烟：`qc doctor` → `[ok] 数据目录: …` / `[ok] data dir: …`，

### 10.18 拼接的文案：`push_notice` / `write!` / `push_str!` 那一整片

§10.17 让英文基线归零后，问了一句「还有遗漏吗」。答案是有一整片，而且成因与
doctor 完全一样：**位置表没覆盖写这些文案的写法**。

**一、漏的是什么。**

| 位置 | 条数 | 写法 |
|---|---|---|
| `qcode/src/commands/sessions.rs` | 15 | `writeln!(report, …)` |
| `qcode-ui-state/actions.rs` | 14 | `push_notice("…")` / `push_notice(format!(…))` / `push_str("…")` |
| `qcode/src/tui.rs` | 12 | `app.push_notice(…)` |
| `qcode-gui/shell/mod.rs` | 7 | `push_notice(format!("cannot save gui.json: {error}"))` |
| `qcode-gui/shell/session.rs` | 5 | 同上 |
| `qcode-core/daemon.rs` | 4 | `write!(f, …)`（`Display` 实现） |
| `qcode-gui/shell/tasks.rs` | 2 | 同上 |
| `qcode/src/commands/gui.rs`、`qcode-gui/shell/view.rs` | 各 1 | 同上 |

合计 61 条。另有 `qcode-tools/{shell,skills}.rs` 与 `qcode-mcp/extras.rs` 的 6 条
（`push_str(&format!(…))`）不在基线里，一并做了。它们当初被排除的理由写在位置表的注释里：「`push_str` / `write!` 是通用
字符串拼装，`qcode-tools/macos.rs` 用它拼 sandbox-exec 的 profile DSL，翻了那条规则
就废了」。**这个顾虑是真的，但代价是整族写法一律不查**——工具结果、TUI 提示、GUI
notice 全在缝里。

**二、修法：收进来，用文件级豁免挡住真会坏的那一处。**

位置表新增 `push_notice(` / `write!(` / `writeln!(` / `push_str!(`，同时在豁免表加
`sandbox/macos.rs`（profile DSL：`(allow file-read*` 是喂给 `sandbox-exec` 的脚本，
翻一个括号就**静默**失效）。规则从「这族写法不查」变成「查，唯一的例外点名豁免」。

**三、`literal_after` 第二次失效，形状和第一次不同。**

第一版扩完后门禁报 24 条，但 `push_notice(format!("…"))` 一个都没报——因为
`literal_after` 又要求「标记后立刻是引号」，而这里引号前面有 `format!(`。
§10.17 那次也是这个病，那次我改成循环调 `literal_after`，**没根治**。

这次按**括号配平**取整个调用内部的全部字面量（`literals_after`），两种形状一次覆盖：
`self.ok(key, "detail")` 取到两个（标签被 `is_key` 滤掉），
`push_notice(format!("…"))` 取到里面那个。截到配平的 `)` 为止，不会把下一条语句的
字面量算进来——第一版「往后扫几行」正是造无关基线条目的原因。

**四、三条新规则，都是从误报里长出来的。**

1. **`Debug` 实现豁免，`Display` 不豁免。** `write!(f, "AttachmentId({})")` 是调试
   表示，不算文案。但第一版判据写成「第一个参数是 Formatter」→ 把
   `NotInstalled` 的 `Display` 也杀了，而那是 `qc daemon: {error}` 打到屏幕上的行动
   提示。改成「往回找最近的 `impl` 头，是 `Debug` 才跳」。
2. **`键=值` 数据列豁免。** `"{id}  turns=3  cost=$0.1  model=x  cwd=/y"` 与
   `qc config show` 同类：字段名要能稳定 grep 和对账。判据是「行首（跳空白）就是
   `标识符=`」或「含 ≥2 个 `名字=`」——`turns=` 算数据，`deleted 3 session(s)` 不算，
   所以后者照翻。
3. **`is_placeholder_only` 继续管 `write!(report, "{}\n", …)`。**

**五、反向验证（这次从一开始就做）。**

把 `actions.rs` 一条 `tr("core.notice.no_file_changes")` 换回
`push_notice("no file changes in this session".to_string())` → 门禁红、点名该文件该行；
恢复 → 绿。**§10.17 的教训是：不反向验证，`literals_after` 这种「静默取不到」的 bug
会以「门禁已覆盖」的假象长期留着。**

**六、新增 47 个 key，分四处落。**

| 命名空间 | 条数 | 归属 |

| `core.notice.*` | 20 | 斜杠命令回话（UI 状态机，跨 TUI/GUI 共用） |
| `tui.notice.*` | 12 | TUI 专属（`qc tui` 的 notice） |
| `gui.notice.*` | 15 | GUI 专属 |
| `cli.session.*` / `tool.*` / `core.daemon.*` | 12 | 各 crate 自己的输出 |

副作用：`qcode-mcp` 新增 `qcode-i18n` 依赖（`extras.rs` 的截断提示）。

**七、翻译规矩（沿用并有新增）。**

- 斜杠命令名（`/diff`、`/unsteer`）、参数占位（`<n>`）、按键（`Esc`、`Ctrl-B`）、
  文件名（`gui.json`）、命令名（`qc skills list`）**不翻**：用户要照着敲/按。
- `%{0}` 位置的运行期事实（错误串、ID、字节数）不翻，只翻它周围的散文。
- 「斜杠命令名 + 中文」混排时用反引号包住命令名，避免中文标点吃掉边界。

**九、测试跟着语言走，不是把断言改松。**

这一批接线后，`qcode-ui-state` 的测试红了 3 个、`qcode-tools` 红了 1 个——它们断言的是

- `ui-state`：按仓库既有惯例钉语言（`qcode_i18n::pin_for_tests()` → 中文），把 12 处

### 10.19 走返回值的错误串：`Err(…)` / `#[error]`，以及 ADR-0105 §5 那条线

§10.18 收尾时英文基线是 0。这次再问「还有遗漏吗」，答案是**一整类**：错误值。

**一、漏的是什么。**

位置表按「输出调用」判（`println!` / `ToolOutput::*` / `push_notice`），而
`Err(format!("no such session: …"))` 是**构造返回值**，不是输出。`main.rs` 统一
`eprintln!("error: {err}")`，所以每一条最终都会原样打到用户眼前——
`QCODE_LANG=zh-CN qc sessions delete nope` 出英文就是这么来的。

新增四条位置：`Err(` / `.ok_or_else(` / `.ok_or(` / `.map_err(|`，以及
`#[error(`——`thiserror` 的属性宏**生成** `Display`，正文全在这里，既不是
`println!` 也不是 `Err(...)` 的实参。实测 `thiserror` 接受**表达式参数**，
所以这批能低成本还。基线一次从 0 涨到 331。

**二、先划边界，再还账：ADR-0105 §5 说的是「工具诊断保持英文」。**

这 331 条里混着两类：

| 类别 | 条数 | 处理 |
|---|---|---|
| `ToolError::*` 的技术诊断（`diff is empty` / `invalid hunk header`） | 63 | **不翻**：`tail` 里出现 `ToolError::` 就跳过（正在构造诊断，不是散文） |
| `qcode-core/todo.rs` 的 `todo_write` 参数诊断 | 11 | **不翻**：整个文件进 `intentional_english`（它照的就是「点名哪个字段、哪个上限」写的） |
| 其余（用户读的错误正文） | 257 | 翻 |

这条线不画清楚，就会把「模型改参数用的诊断」翻成中文——ADR 明说受众是模型。
反向验证两条已写成单测（`tool_error_diagnostics_stay_english`）：
`Err(ToolError::Invalid("diff is empty"))` 不算文案；同一位置上
`Err(format!("item {number} has empty ..."))` 仍要抓。

**三、`#[error]` 怎么翻。**

属性宏只收格式串**字面量**，所以不能把 `tr()` 嵌进去。写法是把整句换成一个
占位符 + 表达式参数：

```rust
#[error("{}", qcode_i18n::trp("core.err.schedule.range", &[.value.to_string(), …]))]
Range { field: String, value: u32, min: u32, max: u32 },
```

- `tr`（无参）/ `trp`（有参）返回 `Cow` / `String`，都实现 `Display`；
- 字段访问用 `.0` / `.detail`，**方法调用也认**（`.0.as_str()`、`.detail.as_str()`），
  这是先在一个变体上试过才铺开的；
- `trp` 的 `&[S]` 要求**同一类型**：混着 `&str` 与 `String` 会 E0308，统一成
  `String` 或统一 `&str`；
- clippy 会盯 `&[x.to_string()]`（`x` 已是 `&String`）→ 用 `.as_str()`。

占位符写 `%{0}`（rust-i18n 语法），不要写 `{}`——那是 `format!` 的。

**四、第一批：`qcode-core` 93 → 0。**

| 文件 | 条数 | 形状 |
|---|---|---|
| `schedule.rs` | 18 | `CronError` / `RuleError` + 拼 `reason`（`expected `daily HH:MM`` 这类） |
| `todo.rs` | 11 | 文件级豁免（见上） |
| `scheduler.rs` | 9 | `ScheduleError` + 校验（标题/提示词/一次性任务必须在将来） |
| `store.rs` | 11 | `StoreError`（`session not found` / `non-monotonic seq` / 锁） |
| `task.rs` | 9 | `TaskError` 校验，5 条带 `MAX_ROOTS` / `80` 这类上限 |
| `tool.rs` | 6 | `ToolError` 变体，**全部 `// i18n:keep`** |
| `title.rs` | 5 | 手写 `Display` 的 `Failed(String)` 载荷 |
| `agents.rs` / `policy.rs` / `single_instance/*` | 12 | `AGENTS.md` 校验、审批规则 glob、单实例 socket |

**五、测试跟着语言走，这次是反方向：不要钉英文。**

`qcode-tools/sandbox/tests.rs` 里四条断言检查 `describe()` 里的英文散文
（`"extra read"` / `"network allowed"` / `"proxy-only on localhost:43123"`）。
宿主是 zh-CN 时 `describe()` 出中文，两个 landlock 测试就红——问题不在翻译，而在
断言钉了英文。改成钉**值**：被授的路径、端口、`tr()` 的取值（`"pty"` 两种语言都
出现，不动）。这样 en / zh 两种宿主都成立，也不去动进程级语言开关
（`CURRENT_LOCALE` 是全局的，`pin_for_tests()` 是 `Once`，谁先跑谁赢）。

**六、`check-i18n-golden.sh` 的颜色检查在 Linux 上是假红。**

颜色检查先用 `script -q /dev/null cmd …`（macOS 的参数顺序）造伪 TTY，失败再回退
到 util-linux 的 `-c`。判据是 `[ -z "$out" ]`——而 util-linux 上第一条会先打一行
`invalid option` 并以非零退出，**那行错误让 `$out` 非空**，回退永远走不到。于是
Linux（含 CI 的 ubuntu 行）一直误报「en 路径丢了颜色」。改成两种写法都试、以输出
里有没有转义码为准。

  「`skills (1)` 或 `技能（1 个）`」两种都认——沿用 `usage` 那几处的既有写法。
